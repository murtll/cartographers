# Локальное окружение: разрабатывать, запускать, тестировать бэкенд

Всё, что нужно, чтобы поднять проект у себя и начать писать код на сервере. Версии
ниже — те, на которых всё проверено и работает.

## Что поставить

Два инструмента, больше ничего:

- **Go** — сейчас `go1.26.5`. В `backend/go.mod` написано `go 1.26`, значит младше
  нельзя, старше можно. Зависимостей в `go.mod` пока нет ни одной, весь сервер стоит на
  стандартной библиотеке — поэтому он собирается и без сети. Первая зависимость появится
  вместе с подключением к базе.
- **Docker** с плагином compose — сейчас Docker `29.6.2`, Compose `v5.3.1`. Проще
  всего Docker Desktop, он тянет и то и другое.

Проверить:

```sh
go version
go env GOTOOLCHAIN   # должно быть auto
docker compose version
docker info          # если ругается — демон не запущен, включи Docker Desktop
```

`GOTOOLCHAIN=auto` — это значение по умолчанию, и его лучше не трогать. С ним Go, увидев
в `go.mod` версию новее установленной, сам скачает нужную. Если поставить `local`, то на
Go 1.25 проект просто не соберётся:

```
go: go.mod requires go >= 1.26 (running go 1.25.x; GOTOOLCHAIN=local)
```

Всё остальное — Postgres, Node, зависимости фронта — живёт в контейнерах, на машину
ставить не надо. `psql` в том числе: если нужно залезть в базу, это делается через
контейнер, команда ниже.

## Первый запуск

```sh
cp .env.example .env
docker compose up
```

Первая команда обязательна, и её легко забыть. Без `.env` compose подставит в
переменные пустые строки, а образ Postgres без пароля просто не стартует. Выглядит это
так — ищи в выводе `variable is not set`:

```
time="..." level=warning msg="The \"POSTGRES_PASSWORD\" variable is not set. Defaulting to a blank string."
```

Коварство в том, что `docker compose config` при этом завершается успешно — он только
предупреждает. Падает всё уже на запуске, и настоящая причина («You must specify
POSTGRES_PASSWORD to a non-empty value») улетает в логи `db`, а на экране остаётся
невнятное `dependency failed to start`. Быстрая проверка, что переменные подставились:

```sh
docker compose config | grep DATABASE_URL
```

Если там `postgres://:@db:5432/?sslmode=disable` — пусто и логин, и пароль, и имя базы.
Значит `.env` нет.

Ещё одна ловушка того же рода: **переменные из шелла сильнее `.env`**. Если в профиле
когда-то был экспортирован `POSTGRES_USER`, compose возьмёт его, а не значение из файла,
и получатся необъяснимые ошибки авторизации. Лечится `unset POSTGRES_DB POSTGRES_USER
POSTGRES_PASSWORD`.

Дальше поднимаются три сервиса:

| сервис     | что это                        | порт | образ              |
|------------|--------------------------------|------|--------------------|
| `db`       | Postgres, сейчас 17.10         | 5432 | `postgres:17-alpine` |
| `backend`  | наш сервер, собирается из исходников | 8080 | собирается локально, ~26 МБ |
| `frontend` | Vite в режиме разработки       | 5173 | `node:lts-alpine`  |

`backend` не запустится, пока `db` не ответит на healthcheck — это прописано в
`docker-compose.yml` через `depends_on: condition: service_healthy`. Так что «сервер
упал, потому что база ещё не поднялась» тут случиться не может.

Образ сервера собирается в два этапа: сначала `golang:1-alpine` с полным тулчейном, потом
всё это выбрасывается, и в финальный образ кладётся только собранный статический бинарник
— отсюда и 26 МБ. Тег `golang:1-alpine` плавающий, но сейчас внутри него та же версия Go,
что и на машине, `1.26.5`, так что локальная сборка и сборка в контейнере совпадают. Если
однажды разойдутся — это первое место, где стоит посмотреть.

Фронтенд создан обычным шаблоном Vite:

```sh
npm create vite@latest frontend -- --template react-ts
```

Проверить, что всё живо:

```sh
curl localhost:8080/healthz     # {"status":"ok"}
open http://localhost:5173      # страница-заглушка Vite
```

Про `/healthz` важно понимать, что он сейчас **ничего не проверяет**: сервер отдаёт
захардкоженную строку и до базы даже не дотягивается. Зелёный ответ значит только «процесс
жив и слушает порт». Базу надо смотреть отдельно:

```sh
docker compose exec db psql -U cartographers -d cartographers -c 'select 1'
```

Сделать `/healthz` настоящим — отдельная задача
[«Подключение к Postgres и честный healthz»](tasks/m05-db-connect.md): он должен ходить
в базу, а не отдавать константу.

**Первый запуск долгий, и это не значит, что что-то повисло.** Скачивается около 250 МБ
образов (Postgres, Go-тулчейн для сборки, Node, Alpine), а потом ещё примерно минуту
контейнер фронта ставит npm-зависимости в отдельный том. Пока он этого не сделал, на 5173
ничего нет. Прерывать не надо, следить можно так:

```sh
docker compose logs -f frontend
```

Дальше эти зависимости лежат в томе, и следующие запуски быстрые.

Данные базы тоже лежат в томе и переживают перезапуск. Если нужно начисто:

```sh
docker compose down -v     # -v сносит и тома вместе с базой
```

Это же — самый простой способ поменять пароль базы. Логин и пароль записываются в том
**один раз**, при первой инициализации: поправить `POSTGRES_PASSWORD` в `.env` после
первого успешного запуска недостаточно, база про новый пароль не узнает, и получишь
ошибку авторизации. Сначала `down -v`, потом `up`. (Можно и `ALTER USER` внутри
контейнера, не теряя данные, но тогда `.env` и настоящий пароль разъедутся — и об этом
придётся помнить.)

Ещё мелочь, которая однажды съест вечер: **имя проекта в compose берётся из имени
папки**. Клонировал не в `cartographers`, а в `cartographers-2` — получил другой набор
контейнеров, другую сеть и, главное, другой том, то есть пустую базу. Старый том при
этом продолжает занимать место.

## Как на самом деле писать код

Через compose разрабатывать бэкенд неудобно: на каждое изменение в `.go` придётся
пересобирать образ (`docker compose up --build`), а это десятки секунд на каждую
опечатку. Правки в `backend/` в контейнер сами не попадают — там лежит собранный
бинарник, а не исходники.

Поэтому обычный цикл такой: **база в докере, сервер локально**.

```sh
docker compose up -d db        # только Postgres, в фоне
cd backend
go run ./cmd/server            # сервер прямо на машине
```

Сейчас серверу база ещё не нужна, так что `go run ./cmd/server` работает и сам по себе.
Когда появится подключение ([задача](tasks/m05-db-connect.md)), понадобится строка
подключения. Изнутри
контейнера хост базы называется `db`, а с машины — `localhost`:

```sh
DATABASE_URL='postgres://cartographers:local-dev-password@localhost:5432/cartographers?sslmode=disable' \
  go run ./cmd/server
```

Логин, пароль и имя базы — те, что в `.env`.

Порт можно поменять переменной, если 8080 занят:

```sh
PORT=8081 go run ./cmd/server
```

## Команды, которые нужны каждый день

Все запускаются **из каталога `backend/`**. В корне репозитория нет `go.mod`, поэтому
оттуда любая команда, которой нужен модуль (`go build`, `go vet`, `go test` с `./...`),
упрётся в непонятное:

```
pattern ./...: directory prefix . does not contain main module or its selected dependencies
```

Это значит только «ты не в том каталоге». Либо `cd backend`, либо `go -C backend build ./...`.

| команда | зачем |
|---------|-------|
| `gofmt -l .` | показывает файлы с неправильным форматированием. Молчит — значит всё хорошо. Внимание: код возврата у него всегда нулевой, надо смотреть на вывод |
| `go build -o /dev/null ./...` | собирается ли всё, не оставляя за собой мусора |
| `go vet ./...` | ищет то, что компилятор пропускает: забытый аргумент в `Printf`, бесполезное сравнение |
| `go test ./...` | все тесты |
| `go test -race ./...` | то же, но с [детектором гонок](glossary.md#g-race-detector) |
| `go test ./internal/boards/ -v` | тесты одного пакета, с именами тестов |
| `go test ./internal/game/ -run TestИмя -v` | один тест по имени |

Про `go build` отдельно: сейчас в модуле ровно один пакет, и `go build ./...` из-за этого
положит рядом восьмимегабайтный файл `backend/server`. (Правило такое: бинарник
записывается, только если под шаблон попал ровно один `main`-пакет; когда пакетов станет
больше, Go просто выбросит результат.) В git этот файл не попадёт, он в `.gitignore`, но
`.dockerignore` в проекте пока нет — значит бинарник поедет в контекст сборки образа и
будет сбрасывать кеш слоёв на каждой пересборке. Поэтому для проверки «компилируется ли»
надёжнее `go build -o /dev/null ./...`: эта форма не оставляет мусора никогда.

**Пока пакетов с кодом нет, половина таблицы ещё не работает** — и это ожидаемо. Каталоги
`internal/*` содержат только заглушки `.gitkeep`, поэтому:

- `go test ./...` скажет `[no test files]` и завершится успешно. То есть зелёный прогон
  сейчас ничего не доказывает — и с `-race` тоже;
- а `go test ./internal/boards/` и вовсе упадёт с `no Go files in ...`. Это не поломка
  окружения: пакет пустой. Команда заработает, как только в нём появится первый файл
  (тема «разметка планшетов»).

Три команды, которые стоит запускать перед коммитом:

```sh
test -z "$(gofmt -l .)" && go vet ./... && go test -race ./...
```

`test -z` здесь не для красоты. `gofmt -l` печатает список неотформатированных файлов, но
завершается **успешно** — то есть в цепочке через `&&` он ничего не остановит, и всё
пройдёт зелёным с криво отформатированным кодом. `test -z` превращает «список непустой» в
настоящую ошибку.

`-race` тут важен не для галочки: скоро появится [горутина](glossary.md#g-goroutine)
на каждую комнату, и с этого момента гонка станет самой вероятной и самой незаметной
ошибкой в проекте. Без детектора она проявляется раз в неделю и невоспроизводимо.

### Проверка, что пакет `game` остался чистым

Договорённость проекта: `internal/game` не знает ни про HTTP, ни про базу. Проверяется
одной командой — она печатает всё, что пакет тянет за собой:

```sh
go list -deps ./internal/game/... 2>&1 | grep -E 'net/http|pgx' && echo LEAK
```

Ничего не напечаталось — всё в порядке. Появился `LEAK` — куда-то просочился лишний
импорт. Пока пакет пустой, команда осмысленного ответа не даёт; она заработает, когда в
`internal/game` появятся файлы.

## Тесты, которым нужна настоящая база

Часть тестов (пакет `store`) будет работать не с заглушкой, а с настоящим Postgres:
[миграции](glossary.md#g-migration) и SQL надо проверять на
живой базе, иначе смысла в тестах нет. Поднимает её `testcontainers-go` — библиотека
сама запускает контейнер на время тестов и убивает после.

Из этого следует ровно одно требование к окружению: **Docker должен быть запущен**.
Если демон не поднят, эти тесты падают с ошибкой подключения, а не пропускаются.

Четыре правила для такого теста, каждое из которых стоило отдельной отладки:

- `flag.Parse()` вызывается в `TestMain` **первым делом** — иначе флаги вроде
  `-test.short` не разберутся;
- перед снятием снапшота базы надо закрыть **все** соединения, иначе Postgres
  откажется;
- контейнерную базу нельзя называть `postgres` — это служебное имя, снапшот по нему
  не снимется;
- в этом пакете не ставим `t.Parallel()`: тесты делят одну базу.

## Линтер

Помимо `go vet` используется `golangci-lint`, версия прибита — `v2.12.2`. Он ставится
**бинарником**, а не через `go install` в зависимости проекта: линтер не должен попадать
в `go.mod`, иначе он тянет за собой полсотни чужих модулей в зависимости сервера.

Сейчас его нет ни локально, ни в CI, и конфига `.golangci.yml` в репозитории тоже нет —
это [отдельная задача](tasks/m05-ci.md), до неё ещё не дошли. Так что если запустить `golangci-lint`, будет
`command not found`, и это ожидаемо, а не сломанное окружение.

## Про секреты

`.env` в репозиторий не попадает — он в `.gitignore`, проверить можно так:

```sh
git check-ignore -v .env      # .gitignore:2:.env	.env
```

Пароль базы лежит только там. В `.env.example` — заведомо игрушечные значения для
локалки, их достаточно, чтобы всё поднялось, и они никуда не годятся дальше.

Позже к ним добавится ключ подписи cookie. Он тоже берётся из переменной окружения и
тоже не коммитится. Правило простое: **секрет, попавший в историю git, из неё уже не
убирается** — его придётся считать скомпрометированным и менять. Поэтому проще не
класть.

## Если что-то не работает

| симптом | причина и что делать |
|---------|----------------------|
| `variable is not set. Defaulting to a blank string` | нет `.env` → `cp .env.example .env` |
| `dependency failed to start: container ...-db-1 exited (1)` | то же самое: база не поднялась без пароля. Причину видно в `docker compose logs db` |
| `port is already allocated` | порт занят. Кем: `lsof -nP -iTCP:5432 -sTCP:LISTEN`. Если это наш же старый запуск — `docker compose down`. Если чужой Postgres — поменять только внешний порт: `"5433:5432"` |
| `directory prefix . does not contain main module` | go-команда запущена из корня → `cd backend` |
| на 5173 пусто, а контейнер запущен | ещё идёт первый `npm install`, подождать минуту. Смотреть: `docker compose logs -f frontend` |
| `sh: vite: command not found` при `npm run dev` в `frontend/` | зависимости фронта лежат **только внутри docker-тома**, а `frontend/node_modules` на машине — пустая папка-точка монтирования. Либо работать через compose, либо сделать `npm install` у себя, погасив перед этим контейнер |
| `frontend/package-lock.json` изменился сам | контейнер фронта на каждом старте делает `npm install` прямо в примонтированную папку и переписывает лок-файл. Не мистика; лок-файл держим в гите |
| поправил код в `backend/`, в браузере старое | контейнер собран из старых исходников → `docker compose up --build backend`. Или, что удобнее, запускать сервер локально через `go run` |
| база помнит старые таблицы после правки миграции | том пережил перезапуск → `docker compose down -v` |
| `password authentication failed` после правки `.env` | пароль вшит в том при первой инициализации → `docker compose down -v`, потом `up` |
| тесты `store` падают на подключении | не запущен Docker |
| `docker info` ругается на демон | Docker Desktop не запущен |

Логи одного сервиса:

```sh
docker compose logs -f backend
```
