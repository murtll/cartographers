# Стек: что берём, чего не берём

Итог: **пять [модулей](glossary.md#g-module)**, из них два в бою и три только в тестах. Всё остальное —
[стандартная библиотека](glossary.md#g-stdlib). Это не аскеза ради аскезы, по каждому пункту ниже написано,
что конкретно библиотека дала бы и почему здесь это не окупается.

| слой | берём | версия |
|------|-------|--------|
| роутер | `net/http.ServeMux` | — |
| SSE | руками на `net/http` | — |
| Postgres | `github.com/jackc/pgx/v5` + `pgxpool`, напрямую | v5.10.0 |
| миграции | `github.com/golang-migrate/migrate/v4` (`iofs` источник на `embed.FS`) | v4.19.1 |
| конфиг | `os.Getenv` + `errors.Join` | — |
| логи | `log/slog` | — |
| разбор JSON | `encoding/json` + один хелпер | — |
| подпись cookie | `crypto/hmac` + `crypto/sha256` | — |
| коды комнат | `crypto/rand` + Crockford base32 | — |
| тестовая база | `testcontainers-go/modules/postgres` | v0.43.0 |
| сравнение в тестах | `github.com/google/go-cmp` | v0.7.0 |
| тесты на время и горутины | `testing/synctest` | — |
| линтер | `golangci-lint` — бинарник в CI, не зависимость | v2.12.2 |
| браузер | родной `EventSource` | — |

```
require (
	github.com/jackc/pgx/v5 v5.10.0 // драйвер + пул, без database/sql
	github.com/golang-migrate/migrate/v4 v4.19.1 // раннер миграций, source/iofs на embed.FS
)

require (
	github.com/google/go-cmp v0.7.0                                 // тесты: читаемый diff
	github.com/testcontainers/testcontainers-go v0.43.0             // тесты
	github.com/testcontainers/testcontainers-go/modules/postgres v0.43.0
)
```

## Почему pgx напрямую, а не через `database/sql`

`database/sql` — общий [интерфейс](glossary.md#g-interface) к любой [SQL](glossary.md#g-sql)-базе, и всё специфичное для Postgres
через него достаётся только через люк `sqlConn.Raw(...)` с приведением типов. А
специфичное для Postgres нам как раз и нужно: `LISTEN/NOTIFY` (план рассылки между
репликами, вместо Redis), пакетная отправка, [`jsonb`](glossary.md#g-jsonb) нормальным типом. Взамен
`database/sql` не даёт ничего — второй базы в проекте не будет.

## Почему `go-migrate`, а не свой раннер

Раньше здесь планировался свой раннер на ~70 строк — прочитать вшитые файлы,
взять advisory lock, применить недостающее, записать sha256 тела в
`schema_migrations`. Решили не писать: `golang-migrate/migrate` — живая, широко
используемая библиотека, закрывающая то же самое без своего кода на
поддержке:

- сам берёт advisory lock на время прогона (драйвер `database/postgres`) —
  не нужно вручную возиться с захваченным соединением и `defer` на разлок;
- умеет `iofs` источник прямо на `embed.FS` — файлы всё так же вшиты в бинарник;
- поддерживает `up`/`down`-миграции из коробки.

Не бесплатно: `go-migrate` не считает [контрольную сумму](glossary.md#g-checksum)
тела файла — учёт идёт по номеру версии и флагу `dirty` в `schema_migrations`, а не
по содержимому. Поправленный задним числом уже накатанный `.sql` он не поймает —
это единственное, что свой раннер умел, а библиотека нет. Дисциплина «старый файл не
трогать, только новая миграция» теперь держится на договорённости, а не на коде.

## Почему нет роутера

`ServeMux` c Go 1.22 умеет `"POST /api/rooms/{code}/moves"`, `r.PathValue("code")`,
сам отдаёт 405 с [заголовком](glossary.md#g-headers) `Allow`. Ручек у нас пять штук. `chi` — честный
второй номер (живой, без зависимостей, с [SSE](glossary.md#g-sse) дружит), но всё, ради чего его берут —
группы, монтирование подроутеров, свои обработчики 404/405 — на пяти плоских
[ручках](glossary.md#g-handler) не нужно.

`gin` тащит ассемблерный JSON-JIT, quic-go, protobuf и [драйвер](glossary.md#g-driver) mongo. `echo`
заменяет `http.Handler` на свой тип. `fiber` вообще не на `net/http` — там нет ни
`http.Flusher`, ни `ResponseController`, то есть SSE пришлось бы писать по-другому.

## Почему SSE руками

Всё, что даёт любая SSE-библиотека, — это брокер (кто на что подписан) и [буфер](glossary.md#g-chan-buffer)
[переигровки](glossary.md#g-replay) (что доотправить после обрыва). У нас брокер это [актор](glossary.md#g-actor) комнаты, а буфер
переигровки — [лог событий](glossary.md#g-log) в Postgres. Библиотека принесла бы вторую копию обоих, и
они бы конкурировали.

`tmaxmax/go-sse` — лучший из живых, но именно с этой архитектурой конфликтует.
`r3labs/sse`, `alexandrevicenzi/go-sse`, `donovanhide/eventsource` — последние
релизы 2023, 2020 и никогда.

## Почему `log/slog`, а не zap/zerolog

Замерили: JSON-запись в slog это 566 нс и ноль аллокаций, вызов ниже уровня — 10 нс.
zerolog экономит ~450 нс на строку. За партию строк несколько сотен. Экономия за всю
игру — доли миллисекунды.

## Почему `go-cmp`, а не `testify`

`testify` популярнее, и `require.NoError` приятнее трёх строк. Но когда не сходится
поле 11×11, `go-cmp` печатает пять строк `(-want +got)` с конкретной клеткой, а
`testify` — два полных дампа структуры, в которых надо глазами искать различие.
Для человека, который читает свой первый падающий тест, это решающе.

## Что ещё смотрели и не взяли

`sqlc` (генерация Go из SQL) — взвешивали честно, генерируемый код читаемый; не
взяли, потому что на пяти запросах ставить кодогенератор в сборку невыгодно. [ORM](glossary.md#g-orm)
(GORM, ent, bun) — прячут ровно тот SQL, который здесь хочется видеть глазами.
`lib/pq` — сами авторы в README отправляют на pgx. `viper` — 17 модулей ради семи
переменных окружения, и `GetString` на отсутствующем ключе возвращает `""` вместо
ошибки. `@microsoft/fetch-event-source` — не обновлялся с 2021 и по умолчанию
рвёт поток, когда вкладка уходит в фон.
