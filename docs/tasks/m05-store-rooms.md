# M0.5 · База данных · store: комнаты

**Фаза 3.** Нужно сначала: [m05-db-migrate-runner.md](m05-db-migrate-runner.md),
[m05-db-connect.md](m05-db-connect.md).
**Результат:** комнату можно создать и найти по коду, занятый код даёт отдельную
понятную ошибку.

Пакет: `backend/internal/store/`. Раздел плана: «Шаг 5. Пакет `store` — чтение и запись
событий», строки 1129–1199.

---

## Зачем это

`store` — единственное место в проекте, которое ходит в Postgres. Всё остальное
работает через него. Задача делится надвое: комнаты (тут) и
[лог событий](../plans/20260728-cartographers-m05.md#g-log)
([m05-store-events.md](m05-store-events.md)). Начинаем с комнат, потому что без строки в
`rooms` события писать некуда — у `events.room_id` стоит
[`REFERENCES rooms(id)`](../plans/20260728-cartographers-m05.md#g-fk), и база не примет
событие несуществующей комнаты.

Что не работает, пока этой задачи нет:

1. **Код комнаты живёт только в памяти.** Сгенерировали, показали игроку, перезапустили
   сервер — комнаты больше нет. Второй игрок вводит код и получает «не найдено».
2. **Нет `room_id`.** `Append` и `EventsSince` принимают его первым аргументом. Взять его
   неоткуда.
3. **Занятый код превращается в тихую беду.** Про это ниже целый раздел «Грабли»: почти
   правильная обработка ошибки Postgres даёт вечный цикл, а не сообщение игроку.

---

- [ ] Объявить [интерфейс](../plans/20260728-cartographers-m05.md#g-interface) на пять методов целиком

Раскладку файлов внутри пакета план не фиксирует — из шага 3 там уже лежит `migrate.go`.

## Интерфейс на пять методов

В плане он записан так:

```
CreateRoom(code, boardID)
Append(roomID, seq, type, payload)
EventsSince(roomID, seq)
FindRoomByCode(code)
ListOpenRooms()
```

Это эскиз: типы, возвращаемые значения и `context.Context` в нём не проставлены. Три
метода из пяти — про комнаты, ими и занимаемся; `Append` и `EventsSince` — соседняя
задача.

Зачем вообще [интерфейс](../plans/20260728-cartographers-m05.md#g-interface), если реализация
одна: он стоит двадцать строк, зато база подменяется в тестах и при желании меняется
целиком отдельным файлом. [ORM](../plans/20260728-cartographers-m05.md#g-orm) не берём — на
весь проект пять запросов, и это ровно тот
[SQL](../plans/20260728-cartographers-m05.md#g-sql), который хочется видеть глазами.

Состав структуры комнаты в Go план не описывает. Известны только колонки
[таблицы](../plans/20260728-cartographers-m05.md#g-table) из шага 3:

```sql
CREATE TABLE rooms (
  id         uuid PRIMARY KEY,
  code       text NOT NULL UNIQUE,
  board_id   text NOT NULL,
  created_at timestamptz NOT NULL DEFAULT now()
);
```

---

## Что уже решено

**`id` генерирует Go, а не база.** У колонки нет `DEFAULT`, а в зависимостях лежит
`github.com/google/uuid` с комментарием «id комнат нормальным типом».
[`uuid`](../plans/20260728-cartographers-m05.md#g-uuid) на то и придуман: значение можно
сделать где угодно, не спрашивая базу. Значит `room_id` известен ещё до `INSERT`, и его
не надо вычитывать обратно.

**Уникальность кода держит база.** `code text NOT NULL UNIQUE` — это
[уникальный индекс](../plans/20260728-cartographers-m05.md#g-unique) `rooms_code_key`.
Соблазн проверить занятость самому — «сначала `SELECT`, если пусто, то `INSERT`» — не
работает: между двумя запросами успевает влезть чужой `INSERT`, и код всё равно окажется
занят, только теперь молча. Надёжный способ ровно один: попробовать вставить и разобрать
ошибку.

**pgx v5 напрямую, без `database/sql`.** Иначе позже будут недоступны нужные возможности
Postgres: `LISTEN/NOTIFY`, пакетная отправка,
[`jsonb`](../plans/20260728-cartographers-m05.md#g-jsonb) нормальным типом. Второй базы в
проекте не будет, так что общий слой не даёт взамен ничего.

**Код комнаты `store` не придумывает.** Его генерирует
[m05-session-room-codes.md](m05-session-room-codes.md) через `crypto/rand` и Crockford
base32. Длина кода в плане не зафиксирована. Здесь код — просто строка на входе.

**`ListOpenRooms()` пока никто не вызывает.** В пяти ручках шага 7 её нет, и колонки
статуса в `rooms` тоже нет — по какому признаку комната «открытая», ещё не решено. Метод
в интерфейсе есть, потребителя нет.

## Тесты на настоящем Postgres

SQLite для тестов при Postgres в бою не заводим: разъедется от особенностей
[SQL](../plans/20260728-cartographers-m05.md#g-sql) до типов данных. `testcontainers-go`
поднимает настоящий Postgres, старт около двух секунд на пакет.

В [`TestMain`](../plans/20260728-cartographers-m05.md#g-testmain) три мелочи, каждая стоит
получаса разбирательств:

- `flag.Parse()` должен быть самой первой строкой, иначе `testing.Short()`
  [паникует](../plans/20260728-cartographers-m05.md#g-panic) с `Short called before Parse`;
- перед `postgres.Snapshot()` надо закрыть все соединения, иначе Postgres откажет с 55006:
  `CREATE DATABASE WITH TEMPLATE` не работает при живых подключениях;
- базу в контейнере нельзя называть `postgres` — системную базу не получится дропнуть при
  восстановлении.

И никакого [`t.Parallel()`](../plans/20260728-cartographers-m05.md#g-tparallel) в этом
пакете: восстановление сносит базу целиком, параллельный тест увидит чужое пустое место.

## Грабли

**[Код ошибки](../plans/20260728-cartographers-m05.md#g-sqlstate) 23505 не означает «номер
занят».** Очевидный хелпер

```go
if pgErr.Code == "23505" { return ErrSeqTaken }
```

неверен. 23505 — это «нарушен любой
[уникальный индекс](../plans/20260728-cartographers-m05.md#g-unique)», а их у нас два:
`events_pkey` (составной [первичный ключ](../plans/20260728-cartographers-m05.md#g-pk)
`room_id, seq`) и `rooms_code_key`. То есть `CreateRoom` при совпадении кода комнаты
вернёт `ErrSeqTaken`, [актор](../plans/20260728-cartographers-m05.md#g-actor) увидит «номер
занят», перечитает [`seq`](../plans/20260728-cartographers-m05.md#g-seq), попробует снова —
и так навсегда, потому что причина не в номере. Игрок при этом видит зависший запрос, а в
логах ровным счётом ничего интересного.

Различать по `ConstraintName`, либо разбирать ошибки отдельно в каждом методе. Заодно
обработать 23503 (событие для несуществующей комнаты) и 23514 (тип события не прошёл
[`CHECK`](../plans/20260728-cartographers-m05.md#g-check)) — это уже про
[m05-store-events.md](m05-store-events.md), но живёт в том же разборе ошибок.

Имя для ошибки «код комнаты занят» план не называет. `ErrSeqTaken` в нём фигурирует
только как пример того, чего нельзя возвращать из `CreateRoom`.

**`pool.Close()` намертво виснет на незакрытом `pgx.Rows`.** Не
[таймаут](../plans/20260728-cartographers-m05.md#g-timeout), а
`fatal error: all goroutines are asleep`. Достаточно одного цикла по строкам, который
вышел по ошибке, не закрыв `Rows`. `ListOpenRooms` — как раз запрос на много строк, то
есть единственный из наших трёх методов, где это можно устроить. Отсюда два правила:
читать через `pgx.CollectRows` / `CollectExactlyOneRow` — они закрывают сами; и строго
соблюдать порядок остановки — сначала слить обработчики, потом `srv.Shutdown`, и только
потом `pool.Close()`.

**`RowToStructByNameLax` молча забивает нулями.** Забыл колонку в `SELECT` — получил
структуру с пустым полем и `err == nil`. Для `FindRoomByCode` это выглядит так: комната
нашлась, `board_id` пустой, планшет не грузится, а виновата строчка запроса, на которую
никто не смотрит. Только строгий `RowToStructByName`, и колонки перечислять руками, без
`SELECT *`.

**Про `Append` и отменённый контекст** — грабля есть, но она про события, и лежит в
[m05-store-events.md](m05-store-events.md). Коротко: `r.Context()` в запись не передавать.

## Готово, когда

- [ ] `go test ./internal/store/ -v` зелёный, в выводе видно, как поднимается контейнер с
      Postgres (первый прогон дольше — образ качается)
- [ ] `go test -race ./internal/store/` тоже зелёный
- [ ] Тест: `CreateRoom` дважды с одним кодом. Вторая попытка возвращает ошибку «код
      занят», и это **другая** ошибка, чем при повторном `seq` в `Append`. Проверять
      именно различие, а не «вернулась хоть какая-то ошибка»
- [ ] Тест: `FindRoomByCode` на несуществующий код даёт отдельную ошибку, а не пустую
      комнату с `err == nil`
- [ ] Тест: у найденной комнаты `board_id` не пустой — это ловушка на `...Lax`
- [ ] Прогон тестов **завершается**. Если увидел `fatal error: all goroutines are asleep`
      — где-то остался незакрытый `Rows`
- [ ] Руками: `docker compose up -d db`, потом
      `docker compose exec db psql -U cartographers -d cartographers -c 'select code, board_id from rooms'`
      — строка на месте

Разбор ошибок удобно проверять
[таблицей](../plans/20260728-cartographers-m05.md#g-table-test): «что нарушаем → какую
ошибку ждём». Тогда добавить 23503 и 23514 — это две строчки, а не две новые функции.
