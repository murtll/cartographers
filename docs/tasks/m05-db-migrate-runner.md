## Зачем это

[Миграция](../plans/20260728-cartographers-m05.md#g-migration) — это `.sql`-файл, который
создаёт или меняет [таблицы](../plans/20260728-cartographers-m05.md#g-table). Он лежит в
репозитории. Раннер — код, который эти файлы накатывает: строго по порядку, ровно по
одному разу и одинаково везде.

Без него схему приходится создавать руками в `psql`. Дальше происходит одно и то же:

1. **Базы разъезжаются.** У одного колонка есть, у другого нет. «У меня работает» — это
   как раз оно.
2. **Тестам негде взять схему.** Тесты пакета `store` поднимают чистый Postgres через
   `testcontainers-go` — в нём нет ничего. Схему в него заливает тот же раннер, что и в
   бою. Иначе тесты проверяют схему, которой в проде нет.
3. **Накат в проде становится ручной операцией.** А ручные операции забывают.

Отдельно — [контрольная сумма](../plans/20260728-cartographers-m05.md#g-checksum). Это то,
ради чего раннер вообще свой, и об этом ниже.

## Что делаем

- [ ] `backend/migrations/embed.go` — `//go:embed *.sql` рядом с самими файлами
- [ ] `migrate.go`: прочитать вшитые файлы, отсортировать по имени
- [ ] Взять [advisory lock](../plans/20260728-cartographers-m05.md#g-advisory-lock) на одном
      соединении и снять его через [`defer`](../plans/20260728-cartographers-m05.md#g-defer)
- [ ] Создать `schema_migrations`, если её нет
- [ ] Сверить `sha256` уже применённых файлов — при расхождении вернуть ошибку
- [ ] Применить недостающие, каждую в своей
      [транзакции](../plans/20260728-cartographers-m05.md#g-transaction)
- [ ] Флаг `MIGRATE_ON_START`, по умолчанию `false`
- [ ] Тесты на настоящей базе через `testcontainers-go`

## Почему свои ~70 строк, а не goose

`goose` — самый очевидный кандидат, и он всё-таки не подошёл:

- у goose **нет проверки контрольных сумм**. Поправил опечатку в уже накатанном `.sql` —
  goose скажет «применять нечего, всё хорошо», а файл и база разъедутся навсегда. И
  чинить это потом нечем: файл в репозитории говорит одно, база помнит другое, и никто
  не знает, где правда. Из рассмотренных инструментов эту ошибку не ловит ни один;
- goose тянет [`database/sql`](../plans/20260728-cartographers-m05.md#g-sql) в проект, где
  его больше нигде нет — ради двух таблиц. Мы работаем с pgx напрямую.

Взамен своего кода мы платим ~70 строками, которые надо написать и покрыть тестами. Это
меньше, чем стоит один разъехавшийся `.sql`.

## Как устроен прогон

Плановая формулировка целиком: прочитать вшитые файлы, отсортировать, взять advisory
lock, применить недостающие каждую в своей транзакции, записать в `schema_migrations` имя
и `sha256` тела.

Учётная таблица:

```sql
CREATE TABLE IF NOT EXISTS schema_migrations (
  name   text PRIMARY KEY,
  sha256 text NOT NULL
);
```

Её создаёт сам раннер, а не первая миграция. Причина простая: чтобы решить, применять ли
первую миграцию, надо сначала где-то прочитать, что уже применено. Таблица, которая
создаётся тем же механизмом, что и проверяет, — это круг. Поэтому `IF NOT EXISTS` и
отдельный шаг до самих миграций — но уже **под локом**: `IF NOT EXISTS` не спасает от двух
одновременных `CREATE TABLE`, второй получит `duplicate key value violates unique
constraint "pg_type_typname_nsp_index"`. Дополнительные колонки (например, время
применения) в плане не оговорены.

Дальше на каждый файл ровно три исхода:

- **имени нет в таблице** — применяем;
- **имя есть, сумма совпала** — пропускаем молча;
- **имя есть, сумма другая** — ошибка, сервер не стартует.

Третий случай и есть весь смысл затеи. `sha256` считается по телу файла **байт в байт**,
поэтому ловится не только «переписал запрос», но и «добавил пробел в конце». Побочный
эффект: если гит на чьей-то машине подменит переводы строк на CRLF, сумма тоже разойдётся.
Это не баг раннера, это правильно найденное расхождение — файл действительно другой.

Форма функции примерно такая (точное имя и сигнатура в плане не зафиксированы):

```go
func Migrate(ctx context.Context, pool *pgxpool.Pool) error
```

## Транзакция на каждую миграцию

В Postgres `CREATE TABLE` работает внутри транзакции и откатывается вместе со всем
остальным — не во всех базах это так. Значит, миграция из пяти запросов, упавшая на
третьем, не оставит после себя половину.

Запись в `schema_migrations` идёт **в той же транзакции**, что и тело миграции. Если
разнести их на две, то падение процесса ровно между ними даёт худшее из состояний:
таблицы созданы, а раннер об этом не знает и при следующем старте попробует создать их
заново. Одна транзакция — либо и таблицы, и запись, либо ничего.

Отката (`down`-миграций) в плане нет. Ошиблись — правим новой миграцией, а не старым
файлом. Старый файл трогать нельзя: его сумма уже в базе.

## Файлы и порядок

`.sql` лежат в `backend/migrations/`, там же `embed.go` с директивой
[`//go:embed`](../plans/20260728-cartographers-m05.md#g-embed). Именно там, а не в общей
папке с данными: `//go:embed` берёт файлы только из своего каталога и ниже, вверх по
дереву (`../`) он ходить не умеет — не соберётся. Заодно образ остаётся однофайловым, и
не бывает «локально мигрируется, в контейнере файлов нет».

Порядок применения — сортировка по имени файла. Отсюда следует, что имя обязано задавать
порядок: числовой префикс фиксированной ширины, иначе `10_...` окажется раньше `9_...`.
Конкретная схема именования в плане не выбрана.

## Грабли

**Advisory lock уезжает обратно в [пул](../plans/20260728-cartographers-m05.md#g-pool).**
Взяли `pg_advisory_lock` на соединении из пула, отпустили соединение — блокировка
осталась. Она сессионная, а `Release()` не закрывает сессию: соединение возвращается в
пул вместе с замком. Следующий запуск миграций виснет навсегда — `pg_advisory_lock` ждёт
без таймаута, а отпускать некому. Симптом самый мерзкий: сервер не падает и ничего не
пишет, он просто не стартует.

Отсюда три правила:

- брать **одно** соединение на весь прогон и делать всё на нём. Не «пул», а конкретный
  захваченный коннект: и лок, и миграции, и разлок;
- первым делом на этом соединении — `SET lock_timeout`. Тогда залипшая миграция уронит
  контейнер с внятной ошибкой, а не будет висеть молча. Упавший контейнер видно в
  оркестраторе, висящий — нет. Конкретное значение таймаута в плане не выбрано;
- `defer` на `pg_advisory_unlock` **по тому же соединению**. По другому — no-op: замок
  принадлежит сессии, которая его взяла.

Номер, на котором берём лок, в плане тоже не назван. Важно лишь, что он один и тот же во
всех репликах, иначе лок не защищает ни от чего.

**Миграции при старте и несколько реплик.** Advisory lock делает одновременный старт
безопасным, но не правильным: при раскатке старый под спокойно применит миграции из
файлов нового образа. То есть схема меняется под работающим старым кодом, и лок этому
никак не мешает — он защищает от двух одновременных накатов, а не от несвоевременного.

Поэтому `MIGRATE_ON_START` по умолчанию **false**. Значение по умолчанию выбрано так,
чтобы забытая переменная давала громкую и безобидную ошибку («таблиц нет»), а не тихое
изменение схемы в бою. В `docker-compose.yml` для локалки — `true`. В бою — отдельный
одноразовый сервис с `depends_on: condition: service_completed_successfully`: сначала
миграции отработали до конца, только потом поднимается приложение. Под этот сервис на
шаге 9 появится второй бинарник `./cmd/migrate`.

**Про `pgxpool.New`, которая «подключается» к мёртвому порту** — это соседняя грабля из
того же шага плана, она разобрана в [m05-db-connect.md](m05-db-connect.md).

## Готово, когда

База в докере, сервер локально — как в [local-setup.md](../local-setup.md):

```sh
docker compose up -d db

cd backend
DATABASE_URL='postgres://cartographers:local-dev-password@localhost:5432/cartographers?sslmode=disable' \
  MIGRATE_ON_START=true go run ./cmd/server

docker compose exec db psql -U cartographers -d cartographers -c '\dt'
```

- [ ] После первого запуска в `\dt` видно `rooms`, `events`, `schema_migrations`
- [ ] Второй запуск той же командой не делает ничего: `select * from schema_migrations`
      возвращает те же строки, лог не сообщает о применении
- [ ] Поправил символ в уже накатанном `.sql`, перезапустил — сервер **не стартует** и
      пишет, у какого файла разошлась сумма. Не `migration error`
- [ ] Без `MIGRATE_ON_START` на чистой базе миграции не применяются
- [ ] `go test ./internal/store/...` зелёный. Тестам нужен запущенный Docker —
      `testcontainers-go` поднимает Postgres сам
- [ ] Тест «накатили на пустую базу → накатили второй раз → изменений нет»
- [ ] Тест «подменили тело файла → `Migrate` вернул ошибку»

Проверки на битые случаи удобно писать
[таблицей](../plans/20260728-cartographers-m05.md#g-table-test): строчка «что подменили →
какой кусок текста ошибки ждём».

Сбросить базу и проверить накат с нуля: `docker compose down -v`, потом `up`. Без `-v`
том переживает перезапуск, и старые таблицы останутся.
