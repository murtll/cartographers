# M0.5 · База данных · Схема и первая миграция

**Фаза 1.** Нужно сначала: ничего.
**Результат:** таблицы `rooms` и `events` созданы, и база сама отказывается принимать
неправильные данные.

Пакет: `backend/migrations/`. Раздел плана: «Шаг 3. База и миграции».

---

## Зачем это

Партия живёт в памяти сервера, а сервер перезапускается. Поэтому настоящая партия хранится
в базе, и хранится не как «текущее поле», а как список случившегося —
[лог событий](../plans/20260728-cartographers-m05.md#g-log). Состояние из него получают
[свёрткой](../plans/20260728-cartographers-m05.md#g-fold): взять пустую партию и применить
события по порядку. Подход называется
[event sourcing](../plans/20260728-cartographers-m05.md#g-event-sourcing), лог событий — наш
[источник истины](../plans/20260728-cartographers-m05.md#g-truth).

Значит нужны две [таблицы](../plans/20260728-cartographers-m05.md#g-table): `rooms` — какие
комнаты вообще есть, `events` — что в них происходило.

Почему схема идёт первой и отдельно:

1. **От неё зависит почти всё остальное.** `store`, актор комнаты, ручки API — все читают
   и пишут эти две таблицы. Придумывать колонки по ходу написания актора — гарантированно
   переделывать.
2. **Часть правил охраняет база, а не Go-код.** Два номера события не совпадут, событие
   несуществующей комнаты не запишется, неизвестный тип не пройдёт. Это не украшение: код
   на Go можно обойти багом, ограничение в базе — нет.
3. **Накатанную миграцию нельзя править.** Чем позже находится ошибка в схеме, тем дороже
   она стоит — см. «Грабли».

## Схема

```sql
CREATE TABLE rooms (
  id         uuid PRIMARY KEY,
  code       text NOT NULL UNIQUE,
  board_id   text NOT NULL,
  created_at timestamptz NOT NULL DEFAULT now()
);

CREATE TABLE events (
  room_id uuid        NOT NULL REFERENCES rooms(id),
  seq     bigint      NOT NULL,
  type    text        NOT NULL,
  payload jsonb       NOT NULL,
  at      timestamptz NOT NULL DEFAULT now(),

  PRIMARY KEY (room_id, seq),
  CONSTRAINT events_type_valid CHECK (type IN (
    'room_created', 'player_joined', 'game_started',
    'round_opened', 'move_submitted', 'round_closed', 'game_ended'
  ))
);
```

---

## Почему схема такая

**`PRIMARY KEY (room_id, seq)`** — не только [ключ](../plans/20260728-cartographers-m05.md#g-pk),
но и защита: два процесса не смогут записать [событие](../plans/20260728-cartographers-m05.md#g-event)
с одинаковым номером, второй получит ошибку. Этим закрывается
[гонка](../plans/20260728-cartographers-m05.md#g-race) на закрытии раунда. Номер уникален
внутри комнаты, а не на весь сервер.

**`payload jsonb`** — у разных событий разные поля. Широкая таблица с кучей пустых колонок
неудобна, а таблица на каждый тип события убила бы единый упорядоченный список. Внутрь
[`payload`](../plans/20260728-cartographers-m05.md#g-jsonb) запросами не лазим: читаем лог
комнаты и разбираем в Go.

**`type text` + [`CHECK`](../plans/20260728-cartographers-m05.md#g-check), а не
[enum](../plans/20260728-cartographers-m05.md#g-enum)** — типы событий будут добавляться на
каждом этапе. У enum в Postgres добавленное значение нельзя использовать в той же
[транзакции](../plans/20260728-cartographers-m05.md#g-transaction), а переименовать или
удалить — целая процедура. `CHECK` меняется обычной миграцией.

**`seq` — не `bigserial`.** Он нумеруется внутри комнаты, а не глобально; счётчик держит в
памяти [горутина](../plans/20260728-cartographers-m05.md#g-goroutine)-владелец (это шаг 6,
[m05-room-actor.md](m05-room-actor.md)).

**`code text NOT NULL UNIQUE`** — код комнаты, который игрок вводит руками. Уникальность
обещает база, а не проверка «а нет ли уже такого» перед вставкой: между проверкой и
вставкой всегда влезет второй запрос. Как коды генерируются и какой они длины — в
[m05-session-room-codes.md](m05-session-room-codes.md), длина в плане пока не зафиксирована.

**`REFERENCES rooms(id)`** — [внешний ключ](../plans/20260728-cartographers-m05.md#g-fk).
Событие несуществующей комнаты база не примет. Дешёвая страховка от опечатки в
[`uuid`](../plans/20260728-cartographers-m05.md#g-uuid).

Семь строк в `CHECK` — все события M0.5. Что лежит у каждого внутри `payload`, разбирается
в [m05-room-fold.md](m05-room-fold.md); здесь фиксируются только имена.

## Как файл ложится в каталог

```
backend/migrations/
├── <первая миграция>.sql
└── embed.go            появится вместе с раннером
```

Раннер читает вшитые файлы, сортирует и применяет недостающие — каждую в своей
[транзакции](../plans/20260728-cartographers-m05.md#g-transaction). Сортировка обычная,
строковая, поэтому имя файла обязано сортироваться в том же порядке, в каком миграции надо
применять: номер в начале и с ведущими нулями, иначе десятая встанет между первой и второй.
Конкретную схему имён план не фиксирует — важно только это свойство.

`.sql` лежат прямо в `backend/migrations/`, а не в общей папке с данными, по той же
причине, что и разметка планшетов рядом с загрузчиком:
[`//go:embed`](../plans/20260728-cartographers-m05.md#g-embed) берёт файлы только из своего
каталога и ниже, `../` он не соберёт.

## Грабли

Раздел «Грабли» в шаге 3 плана — про подключение и раннер (`pgxpool.New` не подключается,
[advisory lock](../plans/20260728-cartographers-m05.md#g-advisory-lock) уезжает обратно в
[пул](../plans/20260728-cartographers-m05.md#g-pool), миграции при старте на нескольких
репликах). Они разобраны в [m05-db-connect.md](m05-db-connect.md) и
[m05-db-migrate-runner.md](m05-db-migrate-runner.md). Здесь — то, что ломается в самой схеме.

**Накатанную миграцию нельзя править.** Соблазн очевидный: нашёл опечатку в `.sql`, который
уже применили, поправил, поехали дальше. Обычные инструменты (тот же `goose`) на это скажут
«применять нечего, всё хорошо» — они помнят только имена файлов. Файл и база разъедутся
молча и навсегда: у тебя в репозитории одна схема, в базе другая, и никто об этом не узнает
до первого странного бага. Поэтому наш раннер хранит в `schema_migrations` ещё и
[`sha256`](../plans/20260728-cartographers-m05.md#g-checksum) тела и при расхождении не
стартует. Правильный ход — новая миграция. Локально, пока схема ещё сырая, можно снести том
целиком: `docker compose down -v`, подробности в [local-setup.md](../local-setup.md).

**Ошибка `23505` не означает «номер события занят».** В этой схеме два уникальных
ограничения: `events_pkey` и `rooms_code_key`. Postgres на оба отдаёт один и тот же
[код](../plans/20260728-cartographers-m05.md#g-sqlstate) `23505`. Хелпер вида
`if pgErr.Code == "23505" { return ErrSeqTaken }` соврёт: при занятом коде комнаты актор
решит, что занят номер события, перечитает `seq`, попробует снова — и так навсегда, потому
что причина совсем другая. Различать по `ConstraintName`.

**`bigserial` вместо `bigint` выглядит удобнее и ломает главное.** С `bigserial` номер
раздаёт база, и раздаёт глобально: сквозная нумерация на все комнаты. Тогда «дошли всё,
что после 17» от браузера перестаёт быть номером внутри комнаты
([`seq`](../plans/20260728-cartographers-m05.md#g-seq)), а `PRIMARY KEY (room_id, seq)`
перестаёт быть защитой от гонки — два одновременных писателя просто получат два разных
свежих номера, и оба запишутся. Номер должен назначать владелец комнаты, а база — только
отказывать при повторе.

**`jsonb` — дверь в одну сторону.** Вытащить поле из `payload` в отдельную колонку потом
легко. Убрать колонку обратно в `payload` — нет: это миграция с переносом данных на живой
базе. Поэтому в первой миграции никаких `player_id text`, `round int` «на всякий случай».
Понадобится искать по полю — тогда и вытащим.

**enum кажется строже и стоит дороже.** Он действительно строже `CHECK`, но добавленное
значение нельзя использовать в той же транзакции, а переименовать или удалить — целая
процедура. Типы событий у нас будут добавляться на каждом этапе, то есть цена платится
регулярно, а выигрыш нулевой: `CHECK` ловит ровно то же самое.

**Том Postgres переживает перезапуск контейнера.** Поправил `.sql`, сделал `docker compose
up` — таблицы старые, потому что данные лежат в томе, а не в образе. Симптом «база помнит
старые таблицы после правки миграции» есть в таблице частых ошибок
[local-setup.md](../local-setup.md), лечится тем же `docker compose down -v`.

## Готово, когда

Раннера ещё нет, поэтому первый раз файл накатывается руками. `psql` ставить не надо, он
есть в контейнере:

```
docker compose up -d db
docker compose exec -T db psql -U cartographers -d cartographers < backend/migrations/<файл>.sql
```

- [ ] `\dt` показывает `rooms` и `events`
- [ ] `\d events` показывает `PRIMARY KEY (room_id, seq)`, ссылку на `rooms(id)` и
      ограничение `events_type_valid`
- [ ] Вставили комнату и событие — прошло
- [ ] Вставили второе событие с теми же `room_id` и `seq` — база отказала, в тексте ошибки
      видно `events_pkey`
- [ ] Вставили вторую комнату с тем же `code` — база отказала, в тексте видно
      `rooms_code_key`. Это **другое** ограничение, хотя код ошибки тот же `23505`
- [ ] Событие с `room_id` несуществующей комнаты — отказ, `23503`
- [ ] Событие с `type = 'lol'` — отказ, `23514`
- [ ] Файл накатывается на пустую базу с нуля: `docker compose down -v`, потом заново — без
      ошибок

Тестов на Go тут нет: файл — чистый [SQL](../plans/20260728-cartographers-m05.md#g-sql).
Автоматически его начнут проверять тесты раннера и тесты `store`.
