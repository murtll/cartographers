# M0.5 · База данных · Подключение к Postgres и честный healthz

**Фаза 2.** Нужно сначала: [Конфиг из переменных окружения](m05-config-env.md).
**Результат:** сервер не стартует, если база недоступна, и `/healthz` перестаёт врать.

Пакет: `backend/internal/store/`.

---

## Зачем это

Партия целиком живёт в базе: комнаты и лог событий, из которого собирается состояние
(правила, которые за этим стоят — [docs/game-rules.md](../game-rules.md)). Пока нет
подключения, дальше не двигается ничего — ни миграции, ни `store`, ни комната.

Вторая половина задачи — `/healthz`. Сейчас он отдаёт захардкоженное `{"status":"ok"}` и
до базы даже не дотягивается, про это прямо написано в
[local-setup.md](../local-setup.md). Зелёный ответ значит только «процесс жив и слушает
порт».

Что ломается, пока это так:

1. **Про мёртвую базу узнаёт игрок, а не сервер.** Порт открыт, healthz зелёный, первый
   же запрос падает с 500.
2. **Тому, кто перезапускает сервер, врут.** Проверка живости для того и нужна, чтобы
   на неё смотрел кто-то автоматический. Проверка, которая всегда отвечает «ок», — это
   не проверка, а константа с HTTP-обёрткой.
3. **Отладка съезжает не туда.** «Сервер зелёный, значит дело во фронте» — и полдня
   уходит в другую сторону.

## Почему pgx напрямую, а не `database/sql`

`database/sql` — общий [интерфейс](../glossary.md#g-interface) к любой
[SQL](../glossary.md#g-sql)-базе, и всё специфичное для Postgres
через него достаётся только через люк `sqlConn.Raw(...)` с приведением типов. А
специфичное для Postgres нам как раз и нужно:
[`LISTEN/NOTIFY`](../glossary.md#g-notify),
пакетная отправка, [`jsonb`](../glossary.md#g-jsonb) нормальным типом.
Взамен `database/sql` не даёт ничего — второй базы в проекте не будет.

Значит и [драйвер](../glossary.md#g-driver), и пул берём из одной
библиотеки: `pgx/v5` и `pgxpool` из неё же.

---

## Пул, а не одно соединение

Соединение с базой открывается не мгновенно: TCP, аутентификация, стартовые параметры.
Поэтому соединения держат наготове пачкой и выдают на запрос, а потом забирают обратно.
Это и есть пул.

Одним соединением на весь сервер обойтись нельзя: каждый HTTP-запрос сервер обслуживает
в своей [горутине](../glossary.md#g-goroutine), и они пойдут в базу
одновременно. Одно соединение превратило бы их в очередь.

Обратная сторона пула — целый класс ошибок «оставил что-то на соединении, а оно уехало
обратно в пул». В этой задаче он ещё не стреляет, в
[миграциях](m05-db-migrate-runner.md) — вешает следующий запуск.

Настройки пула (`MaxConns` и прочее) не зафиксированы. Умолчаний pgx хватает.

## Старт: сначала база, потом порт

`main.go` выстраивается так, и порядок тут не случайный:

1. конфиг из окружения — [m05-config-env.md](m05-config-env.md)
2. разметка планшетов — [m05-boards-markup.md](m05-boards-markup.md)
3. пул и `Ping`
4. миграции, если `MIGRATE_ON_START` — [m05-db-migrate-runner.md](m05-db-migrate-runner.md)
5. и только теперь `ListenAndServe`

Порт открывается последним, потому что открытый порт — это обещание. Как только сервер
слушает 8080, к нему постучатся: и браузер, и healthcheck докера. Всё, что может не
получиться, должно не получиться до этого момента, с внятным сообщением в лог и ненулевым
кодом выхода.

Ping — под собственный [контекст](../glossary.md#g-context) с
таймаутом, а не под фоновый:

```go
ctx, cancel := context.WithTimeout(context.Background(), 5*time.Second)
defer cancel()
if err := pool.Ping(ctx); err != nil {
    // не стартуем
}
```

Без таймаута мёртвый хост даёт не ошибку, а зависание: процесс молча стоит, докер по
нему ничего не понимает, в логах пусто.

Имена функции и типа в `internal/store` не зафиксированы. Что она делает — зафиксировано:
берёт строку подключения, открывает пул, пингует, возвращает пул или ошибку.

## Честный `/healthz`

Ручка ходит в базу. Тот же `Ping`, но таймаут короткий: проверку живости дёргают часто,
и висеть на ней нельзя.

- база ответила → 200 и прежнее тело `{"status":"ok"}`, чтобы не ломать
  [local-setup.md](../local-setup.md) и README;
- база не ответила → **не 200**. Конкретный
  [код](../glossary.md#g-status) не выбран; разумно 503.

Чего в ответе быть не должно — текста ошибки драйвера целиком: пароль pgx из строки
подключения вырезает, а хост, логин и имя базы в ошибке остаются. `/healthz` открыт
наружу.

И `Ping` — это не `SELECT` по таблицам. Проверка живости должна быть дешёвой: она
выполняется каждые несколько секунд всё время жизни сервера.

## Грабли

**`pgxpool.New` не подключается.** Она возвращает `err == nil` за 3 миллисекунды, даже
если порт мёртвый. Причина: соединения создаются лениво, при первом запросе. `MinConns`
не помогает. Итог: сервер стартовал зелёным, `/healthz` отвечает 200, а первый игрок
получает ошибку. Лечится одной строкой — `pool.Ping(ctx)` на старте под таймаут в
5 секунд, и падать, если не вышло. И база должна участвовать в `/healthz`, а не отдавать
константу.

Единственное, что `pgxpool.New` действительно проверяет сразу, — что строку подключения
можно разобрать. `postgres://` с опечаткой в схеме отвалится, недоступный хост — нет.

Локально грабля прячется: в `docker-compose.yml` у `backend` стоит
`depends_on: condition: service_healthy`, база там всегда готова. Вылезет она при
`go run ./cmd/server` без поднятой базы — и в бою.

**`pool.Close()` намертво виснет на незакрытом `pgx.Rows`.** Не таймаут, а
`fatal error: all goroutines are asleep`. Достаточно одного цикла по строкам, который
вышел по ошибке, не закрыв `Rows`. Запросов здесь ещё нет, но порядок остановки пишется
именно в этой задаче, и он такой: сначала слить обработчики, потом `srv.Shutdown`, и
только потом `pool.Close()`. Закроешь пул раньше — доигрывающие запросы получат ошибку
ровно в момент
[корректного завершения](../glossary.md#g-shutdown), которое для
того и делалось. Вторая половина правила (`pgx.CollectRows` вместо ручного цикла) — в
[m05-store-events.md](m05-store-events.md).

**Соседние грабли шага 3 — не в эту задачу, но знать про них надо.**
[Advisory lock](../glossary.md#g-advisory-lock) уезжает обратно в
пул: блокировка сессионная, `Release()` соединения сессию не закрывает, и замок
возвращается в пул вместе с соединением — следующий запуск миграций виснет навсегда.
И `MIGRATE_ON_START` по умолчанию **false**: advisory lock делает одновременный старт
нескольких реплик безопасным, но не правильным — при раскатке старый под спокойно
применит миграции из файлов нового образа. Подробно и с лечением — в
[m05-db-migrate-runner.md](m05-db-migrate-runner.md).

## Готово, когда

Всё — из каталога `backend/`.

- [ ] База поднята, сервер стартует, healthz зелёный:

```sh
docker compose up -d db
DATABASE_URL='postgres://cartographers:local-dev-password@localhost:5432/cartographers?sslmode=disable' \
  go run ./cmd/server
curl -i localhost:8080/healthz     # 200, {"status":"ok"}
```

- [ ] Порт, на котором никто не слушает (`localhost:5433`) — сервер падает **за пять
      секунд**, пишет причину, и `curl localhost:8080/healthz` из другого терминала даёт
      `Connection refused`: порт так и не открылся
- [ ] `docker compose stop db` на живом сервере — `curl -i localhost:8080/healthz`
      отвечает **не 200**. Это главный пункт: раньше он отвечал 200 всегда
- [ ] `docker compose start db` — тот же `curl` снова 200, без перезапуска сервера. Пул
      переподключается сам
- [ ] `go test ./internal/store/...` зелёный: строка `не-url` даёт ошибку из
      `pgxpool.New`, база для этого теста не нужна
- [ ] `go vet ./...` чисто, `gofmt -l` пусто
- [ ] Ctrl+C на сервере: процесс выходит сам, без зависания и без паники

Тесты на настоящем Postgres через `testcontainers-go` приедут вместе с запросами —
[m05-store-rooms.md](m05-store-rooms.md). Там же три грабли
[`TestMain`](../glossary.md#g-testmain), каждая стоит получаса.
