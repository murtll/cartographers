# M0.5 · База данных · store: лог событий

**Результат:** события пишутся и читаются по порядку, повтор номера даёт `ErrSeqTaken`,
тесты идут на настоящем Postgres.

событий», строки 1129–1199. Про `seq` и `PRIMARY KEY` — строки 1054–1069.

---

## Зачем это

Партия не хранится как «текущее состояние». Она хранится как
[лог событий](../plans/20260728-cartographers-m05.md#g-log): игрок вошёл, раунд открылся,
игрок поставил клетку. Состояние получается [свёрткой](../plans/20260728-cartographers-m05.md#g-fold)
— берём пустую партию и применяем события одно за другим. Подход называется
[event sourcing](../plans/20260728-cartographers-m05.md#g-event-sourcing), и лог в базе —
[источник истины](../plans/20260728-cartographers-m05.md#g-truth) обо всём, что случилось.

Эта задача — две функции, которые кладут событие в лог и читают лог обратно. Вторая
половина пакета `store`; первая, комнаты, лежит в [m05-store-rooms.md](m05-store-rooms.md).

Что не работает, пока её нет:

1. **Партия не переживает перезапуск.** Состояние живёт только в памяти. Упал процесс —
   упала партия, и восстанавливать нечего.
2. **Отключившийся игрок не догоняет.** Браузер помнит номер последнего полученного
   события и при обрыве просит «всё, что после 17». Отвечать на это нечем — вся
   [переигровка](../plans/20260728-cartographers-m05.md#g-replay) из
   [m05-http-sse.md](m05-http-sse.md) висит на `EventsSince`.
3. **Некому ловить гонку на номере.** Составной ключ по `(room_id, seq)` — последняя
   защита от двух записей с одним номером. Без `Append` эта защита ни разу не
   срабатывает.

---

## Что делаем

- [ ] `Append(roomID, seq, type, payload)` — вставка строки в `events`
- [ ] `EventsSince(roomID, seq)` — всё, что строго после указанного номера, по порядку
- [ ] Реестр типов [событий](../plans/20260728-cartographers-m05.md#g-event): `строка → структура Go`
- [ ] Неизвестный тип при чтении — ошибка, а не молчаливый пропуск
- [ ] Отдельная ошибка `ErrSeqTaken` на повтор номера, и она **не** та же, что «код комнаты занят»
- [ ] Разбор `23503` (событие для несуществующей комнаты) и `23514` (тип не прошёл `CHECK`)
- [ ] Тесты на настоящем Postgres: три события, чтение с середины, повтор номера
- [ ] Тесты «структура в JSON и обратно — то же самое», по одному на каждый тип события

## Таблица, из которой всё следует

Из шага 3, [m05-db-schema.md](m05-db-schema.md):

```sql
CREATE TABLE events (
  room_id uuid        NOT NULL REFERENCES rooms(id),
  seq     bigint      NOT NULL,
  type    text        NOT NULL,
  payload jsonb       NOT NULL,
  at      timestamptz NOT NULL DEFAULT now(),

  PRIMARY KEY (room_id, seq),
  CONSTRAINT events_type_valid CHECK (type IN (
    'room_created', 'player_joined', 'game_started',
    'round_opened', 'move_submitted', 'round_closed', 'game_ended'
  ))
);
```

Четыре решения тут уже приняты, и каждое отражается на коде `Append`.

**`PRIMARY KEY (room_id, seq)` — не только ключ, но и защита.** Два процесса не смогут
записать событие с одинаковым номером, второй получит ошибку. Этим закрывается
[гонка](../plans/20260728-cartographers-m05.md#g-race) на закрытии раунда: внутри процесса
номер стережёт [актор](../plans/20260728-cartographers-m05.md#g-actor), база — последняя
защита. Отсюда и `ErrSeqTaken` — вызывающая сторона обязана уметь эту ошибку узнать.

**`seq` — не `bigserial`.** Он нумеруется внутри комнаты, а не глобально; счётчик держит в
памяти [горутина](../plans/20260728-cartographers-m05.md#g-goroutine)-владелец
([m05-room-actor.md](m05-room-actor.md)). Значит номер приходит в `Append` аргументом,
и `store` его не придумывает и не проверяет — проверяет база.

**`payload jsonb`.** У разных событий разные поля. Широкая таблица с кучей пустых колонок
неудобна, а таблица на каждый тип события убила бы единый упорядоченный список. Внутрь
[`payload`](../plans/20260728-cartographers-m05.md#g-jsonb) запросами не лазим: читаем лог
комнаты и разбираем в Go. Если потом понадобится искать по какому-то полю, вытащить его в
колонку легко, обратно — нет.

**`type text` + [`CHECK`](../plans/20260728-cartographers-m05.md#g-check), а не
[enum](../plans/20260728-cartographers-m05.md#g-enum).** Типы событий будут добавляться на
каждом этапе. У enum в Postgres добавленное значение нельзя использовать в той же
[транзакции](../plans/20260728-cartographers-m05.md#g-transaction), а переименовать или
удалить — целая процедура. `CHECK` меняется обычной миграцией. Плата: неизвестный тип
прилетает не ошибкой компиляции, а `23514` из базы.

## Реестр типов событий

Семь типов, их полезная нагрузка расписана в шаге 6:

```
room_created    { board_id }
player_joined   { player_id, name, slot }
game_started    { seed, deck_order }   ← в проекцию не попадает
round_opened    { round, options, constraint }
move_submitted  { actor, target_board, shape_id, rot, flip, anchor, terrain }
round_closed    { round }
game_ended      { scores }
```

Реестр — это отображение `строка → структура Go`: по `type` из базы понятно, во что
разбирать `payload`. Ключевое правило: **неизвестный тип при чтении — ошибка**. Соблазн
пропустить незнакомую строку и читать дальше выглядит безобидно, но в event sourcing он
смертелен. Пропущенное событие — это не «чуть меньше данных», это другая партия: не
засчитанный ход, не закрытый раунд, разъехавшийся счёт. И заметят это через день, на
готовом поле.

Сами структуры полезной нагрузки и их Go-имена план не фиксирует — есть только состав
полей выше. Имена полей в коде смотри в [game-rules.md](../game-rules.md), раздел «Имена в
коде».

## Грабли

**[Код ошибки](../plans/20260728-cartographers-m05.md#g-sqlstate) 23505 не означает «номер
занят».** Очевидный хелпер

```go
if pgErr.Code == "23505" { return ErrSeqTaken }
```

неверен: 23505 это «нарушен любой
[уникальный индекс](../plans/20260728-cartographers-m05.md#g-unique)», а их у нас два —
`events_pkey` и `rooms_code_key`. То есть `CreateRoom` при совпадении кода комнаты вернёт
`ErrSeqTaken`, [актор](../plans/20260728-cartographers-m05.md#g-actor) увидит «номер занят»,
перечитает [`seq`](../plans/20260728-cartographers-m05.md#g-seq), попробует снова — и так
навсегда, потому что причина не в номере. Различать по `ConstraintName`, либо разбирать
ошибки отдельно в каждом методе. Заодно обработать 23503 (событие для несуществующей
комнаты — сработал [внешний ключ](../plans/20260728-cartographers-m05.md#g-fk)) и 23514
(тип события не прошёл `CHECK`).

**Не передавать `r.Context()` в `Append`.** Под [SSE](../plans/20260728-cartographers-m05.md#g-sse)
[контексты](../plans/20260728-cartographers-m05.md#g-context) запросов отменяются постоянно:
закрыл вкладку, переподключился. Замерено: контекст, отменённый рядом с коммитом, вернул
ошибку — а строка **записалась**. Дальше самое неприятное: `seq` у нас нумеруется в памяти,
значит после «ошибки» актор оставит у себя старый номер, а в базе он уже занят, и
расхождение навсегда. Каждая следующая запись будет натыкаться на занятый номер.

Отсюда два правила. Актор пишет в базу под своим временем жизни —
`context.WithoutCancel` от базового контекста сервера, а не от контекста запроса. И на
**любую** ошибку `Append` — не гадать, записалось или нет, а перечитать лог через
`EventsSince`. База — источник истины, память — производное.

**`pool.Close()` намертво виснет на незакрытом `pgx.Rows`.** Не
[таймаут](../plans/20260728-cartographers-m05.md#g-timeout), а
`fatal error: all goroutines are asleep`. Достаточно одного цикла по строкам, который вышел
по ошибке, не закрыв `Rows`. `EventsSince` — запрос на много строк, и разбор `payload`
внутри цикла даёт ровно тот выход по ошибке. Отсюда два правила: читать через
`pgx.CollectRows` / `CollectExactlyOneRow` — они закрывают сами; и строго соблюдать порядок
остановки — сначала слить обработчики, потом `srv.Shutdown`, и только потом `pool.Close()`.

**`RowToStructByNameLax` молча забивает нулями.** Забыл колонку `payload` в `SELECT` —
получил событие с пустым payload и `err == nil`. Свёртка при этом отработает: применит семь
пустых событий и вернёт пустую партию, без единой ошибки. Это ровно тот молчаливый пропуск,
которого в event sourcing быть не должно. Только строгий `RowToStructByName`, и колонки
перечислять руками, без `SELECT *`.

## Готово, когда

- [ ] `go test ./internal/store/ -v` зелёный, `go test -race ./internal/store/` тоже
- [ ] Тест: записали три события, `EventsSince(roomID, 1)` вернул **два**, в порядке
      возрастания `seq`. Проверять и количество, и порядок
- [ ] Тест: `Append` с уже занятым номером возвращает `ErrSeqTaken`, и это **другая**
      ошибка, чем при повторном коде комнаты в `CreateRoom`
- [ ] Тест: `Append` в несуществующую комнату даёт свою ошибку (23503), а неизвестный
      `type` — свою (23514)
- [ ] Тест: чтение события с типом, которого нет в реестре, возвращает ошибку. Не пустую
      структуру, не пропуск
- [ ] Тест «туда-обратно» на каждый тип: структура → JSON → структура, результат тот же.
      Двадцать строк, ловят опечатку сразу, а не через месяц
- [ ] Прогон тестов **завершается**. `fatal error: all goroutines are asleep` — где-то
      остался незакрытый `Rows`
- [ ] Руками: `docker compose up -d db`, потом
      `docker compose exec db psql -U cartographers -d cartographers -c 'select seq, type from events order by seq'`
      — события на месте и по порядку
- [ ] Руками: вставить два события с одинаковыми `room_id` и `seq` — база должна отказать

Разбор ошибок и реестр удобно проверять
[таблицей](../plans/20260728-cartographers-m05.md#g-table-test): «что нарушаем → какую
ошибку ждём». Тогда новый тип события — это строчка, а не новая функция.

Про [`TestMain`](../plans/20260728-cartographers-m05.md#g-testmain) с `testcontainers-go`,
`flag.Parse()` первой строкой и запрет
[`t.Parallel()`](../plans/20260728-cartographers-m05.md#g-tparallel) — всё это уже сделано в
[m05-store-rooms.md](m05-store-rooms.md), контейнер один на весь
[пакет](../plans/20260728-cartographers-m05.md#g-package).
