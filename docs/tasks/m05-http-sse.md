# M0.5 · HTTP · Поток событий в браузер (SSE)

**Фаза 2.** Нужно сначала: [Роутер и пять путей](m05-http-routing.md), [Логи запросов и
перехват паники](m05-http-middleware.md).
**Результат:** `curl -N` показывает кадры по мере появления, обрыв и переподключение
продолжают поток с нужного места.

Пакет: `backend/internal/api/`.

---

## Зачем это

Состояние партии меняет не только сам игрок: истёк дедлайн раунда — клетку ставит сервер,
а в M2 к нему в комнату сядет сосед. На экране это должно появиться само, без кнопки
«обновить». Обычный HTTP так не умеет: браузер спросил, сервер ответил, соединение
закрылось.

[SSE](../glossary.md#g-sse) — тот же самый HTTP-запрос, только
сервер его **не закрывает**, а дописывает в него строки. Браузерная сторона — встроенный
`EventSource`, её писать не надо.

Без этого игра остаётся перепиской: чтобы увидеть, что изменилось, надо перезагрузить
страницу. И это единственный кусок сервера, который живёт минутами, а не миллисекундами, —
поэтому на нём ломается всё, что рассчитано на короткий запрос: таймауты, обёртки,
остановка.

---

## Что делаем

- [ ] Ручка `GET /api/rooms/{code}/stream`: статус 200 и `Content-Type: text/event-stream`
- [ ] Кадр — `id: <seq>`, `data: <JSON>`, пустая строка
- [ ] Сбрасывать [буфер](../glossary.md#g-flush) после **каждого**
      кадра, через `http.NewResponseController(w).Flush()`
- [ ] Снять дедлайн записи: `SetWriteDeadline(time.Time{})`
- [ ] [Heartbeat](../glossary.md#g-heartbeat) по тикеру, с `id:`
      последнего отправленного кадра
- [ ] Прочитать `Last-Event-ID` и `?from=`, дослать пропущенное, потом продолжить поток
- [ ] Выходить по `r.Context().Done()` **и** по `<-drain`
- [ ] В `main.go`: `srv.RegisterOnShutdown(func() { close(drain) })`, `WriteTimeout` не выставлять
- [ ] У каждой обёртки над `ResponseWriter` в
      [middleware](../glossary.md#g-middleware) — метод `Unwrap()`
- [ ] Временный источник кадров: комнаты ещё нет
- [ ] Тесты — через настоящую цепочку middleware, не через голую ручку

## Как выглядит кадр

```
id: 42
data: {"seq":42,"phase":"cartography","round":7}

```

Пустая строка — конец кадра. Без неё браузер держит его в разборе и не отдаёт ничего.

`id:` — это [`seq`](../glossary.md#g-seq), номер события внутри
комнаты. Он тут не для красоты: браузер запоминает последний увиденный `id` и при обрыве
сам присылает его обратно в [заголовке](../glossary.md#g-headers)
`Last-Event-ID`. То есть логику «что я пропустил» пишет не клиент, а спецификация — на
сервере остаётся прочитать заголовок и отдать хвост.

Что лежит внутри `data` — [снапшот](../glossary.md#g-snapshot)
партии целиком, его состав решается в [m05-room-projection.md](m05-room-projection.md).
Этой задаче содержимое безразлично: она отвечает за то, чтобы байты доехали.

## Порядок действий в ручке

1. Разобрать путь, найти комнату. **Это последнее место, где можно ответить не-200.**
2. Поставить заголовки, отдать 200, сразу сделать `Flush`. Клиент должен увидеть открытый
   поток, а не ждать первого события.
3. Снять дедлайн записи.
4. Подписаться на комнату, потом прочитать `Last-Event-ID` / `?from=` и дослать хвост.
   Именно в таком порядке — иначе между чтением лога и подпиской теряются события.
   Подробности с дедупликацией — в [m05-room-subscribers.md](m05-room-subscribers.md).
5. Цикл [`select`](../glossary.md#g-select) на четыре ветки: новый
   кадр, тик heartbeat, `r.Context().Done()`, `<-drain`.

## Откуда берутся кадры сейчас

[Актора](../glossary.md#g-actor) комнаты и
[лога событий](../glossary.md#g-log) ещё нет — это фаза 3. Значит
источник кадров пока временный: [канал](../glossary.md#g-channel), в
который что-то кладёт готовые кадры, и счётчик `seq` на единицу за кадр. Тема задачи —
механика потока, а не его содержимое.

Заменится это так: [подписчик](../glossary.md#g-subscriber) — один
открытый поток одного зрителя, актор держит их список и рассылает снапшот каждому.

Два числа не выбраны, придумывать их здесь нечего. Размер
[буфера](../glossary.md#g-chan-buffer) у канала подписчика: политика
есть («не влезло — рвём соединение, событие не теряем»), а число до появления настоящих
снапшотов не определить. Период heartbeat — «раз в N секунд».

## Грабли

Здесь их больше, чем в любой другой задаче милестоуна. Каждая замерена, каждая
проявляется не как падение, а как «почему-то не работает».

**Любой не-200 из ручки потока убивает клиента навсегда.** Замерено в Chrome: на 500, 404,
204 и даже на 200 с неправильным `Content-Type` `EventSource` вызывает `onerror`, ставит
`readyState === 2` и **больше не пробует никогда**. Ни через секунду, ни через минуту. То
же самое, если dev-прокси Vite вернул 502, потому что бэкенд ещё не поднялся.

Отсюда правило: как только запрос прошёл проверку и комната найдена — **всегда** 200 и
`text/event-stream`. Всё, что сломается дальше, уезжает сообщением `{"type":"error"}`
внутрь потока, и потом поток закрывается. Кнопку «переподключиться» по `readyState === 2`
рисует браузерная часть, она создаёт `EventSource` заново.

**Обёртка над [`ResponseWriter`](../glossary.md#g-responsewriter)
без `Unwrap()` ломает все потоки.** Обычная middleware, которая запоминает статус ответа:

```go
type rec struct {
    http.ResponseWriter
    status int
}
```

и всё: `w.(http.Flusher)` через неё возвращает `ok == false`, а `Flush()` на nil
[паникует](../glossary.md#g-panic).
`http.NewResponseController(w).Flush()` тоже не спасает — он идёт по цепочке `Unwrap()`, а
её здесь нет, и возвращает `feature not supported`.

Два правила. У **каждой** обёртки есть `func (w *rec) Unwrap() http.ResponseWriter`. Буфер
сбрасываем только через `ResponseController`, никогда через приведение к `Flusher`. И тест
на SSE гонять через настоящую цепочку middleware — голый обработчик этого не поймает.

**`WriteTimeout` рубит поток посреди партии.** Замерено: `WriteTimeout` 250 мс и события
раз в 400 мс — доехало одно из трёх, дальше `i/o timeout`.

Обойтись «включим его только для POST-ручек» не выйдет: `WriteTimeout` — поле
`http.Server`, оно действует на все соединения сразу, отдельного
[таймаута](../glossary.md#g-timeout) на ручку в `net/http` не
существует. Поэтому общий `WriteTimeout` **не выставляем вовсе**. Без присмотра соединения
при этом не остаются: медленный запрос ограничивает `ReadHeaderTimeout`, а срок на
конкретный ответ ставит сама ручка — [контекстом](../glossary.md#g-context)
с дедлайном в POST-ручках и `r.Context().Done()` в потоке.

В SSE-обработчике дедлайн на запись всё равно снимаем явно —
`http.NewResponseController(w).SetWriteDeadline(time.Time{})`, нулевое время это «без
дедлайна». Сейчас снимать нечего, но если `WriteTimeout` однажды кто-нибудь добавит, поток
от этого не оборвётся.

Ошибку от `SetWriteDeadline` при этом **нельзя считать фатальной**. Она возвращает
`ErrNotSupported` на любой обёртке без `Unwrap` и на `httptest.NewRecorder`. Если на ней
выйти из функции — клиент получит 200, один кадр `retry:` и разрыв, и будет
переподключаться каждые две секунды вечно. Игнорируем именно `http.ErrNotSupported`,
падаем на настоящих ошибках.

**`srv.Shutdown()` не отменяет контексты запросов.** Идиоматичный
`case <-r.Context().Done():` внутри SSE-цикла до него просто не доходит: замерено на Go
1.26.5 — `Shutdown` заблокировался на всё время жизни обработчика, а обработчик доложил,
что его контекст никто не отменял. С одной открытой вкладкой каждый деплой выжигает весь
таймаут [остановки](../glossary.md#g-shutdown), пишет
`context deadline exceeded` и потом рвёт соединения силой.

Лечится каналом-сигналом:

```go
drain := make(chan struct{})
srv.RegisterOnShutdown(func() { close(drain) })
```

SSE-обработчик ждёт в `select` не только `r.Context().Done()`, но и `<-drain` — отправляя
перед выходом прощальное событие. После этого `Shutdown` возвращается мгновенно и без
ошибки.

**У heartbeat тоже должен быть `id:`.** Кажется логичным слать
`data: {"type":"heartbeat"}` без номера — «он же не событие,
[переигровку](../glossary.md#g-replay) не трогает». Трогает. По
спецификации браузер обновляет свой буфер последнего id только когда разобрал поле `id:`,
и на свежесозданном `EventSource` этот буфер **пустой**. Клиент делает
`lastSeq = e.lastEventId` — и первый же heartbeat затирает номер пустой строкой. Следующее
переподключение просит `?from=` и переигрывает всю партию с нуля. Поэтому в heartbeat
пишем `id: <последний отправленный seq>` — повтор номера для переигровки безвреден.

**Catch-all на `/` отдаёт HTML в ответ на JSON-запрос со статусом 200.** Это уже про шаг 9,
раздачу собранного фронтенда, но лежит в том же разделе граблей: `mux.HandleFunc("/", ...)`
перехватывает и `DELETE /api/rooms`, и `GET /api/rooms/{code}/moves` — вместо 405 приходит
200 с `index.html`, а `res.json()` падает с `Unexpected token '<'`. Обработчик-заглушка
должен проверять `strings.HasPrefix(r.URL.Path, "/api/")` и отдавать честный JSON-404.

## Готово, когда

- [ ] `curl -N localhost:8080/api/rooms/ABCD/stream` печатает первый кадр сразу, а не
      после накопления буфера, и дальше добавляет кадры по одному
- [ ] В выводе `curl -N` у каждого кадра, включая heartbeat, есть строка `id:`
- [ ] `curl -N -H 'Last-Event-ID: 3' ...` начинает не с начала, а с четвёртого
- [ ] Пока `curl -N` висит, `SIGTERM` останавливает сервер за доли секунды, а не за десять,
      и в логе нет `context deadline exceeded`
- [ ] `go test ./internal/api/` — тест поднимает сервер **через полную цепочку middleware**,
      читает поток и видит кадры. Он должен покраснеть, если убрать `Unwrap()` у обёртки
- [ ] Тест на `Last-Event-ID`: подключились, получили N кадров, оборвали, подключились
      снова с последним id — дырок и повторов в номерах нет
- [ ] `go test -race ./...` зелёный, и после закрытия `curl -N` число
      [горутин](../glossary.md#g-goroutine) возвращается к
      исходному — иначе `Done()` не обрабатывается и они копятся

Тесты на кадры удобно писать
[таблицей](../glossary.md#g-table-test): «что подали → какие строки
ожидаем в потоке». Тесты, где участвует тикер heartbeat, — через `testing/synctest`, иначе
придётся реально ждать секунды.
