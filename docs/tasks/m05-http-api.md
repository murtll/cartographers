Пакет: `backend/internal/api/`.

---

## Зачем это

К этому моменту готово всё, кроме склейки. Роутер отвечает на пять путей константами.
[Актор](../glossary.md#g-actor) умеет применить ход и разослать
[снапшот](../glossary.md#g-snapshot). `store` пишет и читает
[события](../glossary.md#g-event). Подпись
[cookie](../glossary.md#g-cookie) отличает одного человека от другого.
Соединено это ничем.

[Ручка](../glossary.md#g-handler) — единственное место, где HTTP
встречается с комнатой: разобрать [JSON](../glossary.md#g-json),
достать код комнаты из пути, прочитать cookie, положить сообщение актору, дождаться ответа,
выбрать [статус](../glossary.md#g-status). Правил игры в ней нет ни
строчки — они в `game`, порядок действий в `room`. Это последняя задача бэкенда в M0.5:
после неё пункты 2–6 из «Готово, когда» всего этапа проверяются тремя терминалами с `curl`.

---

## Что делаем

- [ ] `POST /api/rooms` — создать комнату, вернуть код
- [ ] `POST /api/rooms/{code}/join` — ник → cookie с местом игрока
- [ ] `POST /api/rooms/{code}/moves` — разобрать ход, отдать актору, дождаться ответа
- [ ] `GET /api/rooms/{code}/stream` — подписка на настоящую комнату вместо заглушки
- [ ] `GET /api/boards/{id}` — разметка планшета
- [ ] Структура-обработчик: то, что ручки держат общего
- [ ] `actor` берём из cookie, а не из тела запроса
- [ ] Поле `round` в ходе: за уже закрытый раунд — молча выбросить
- [ ] Срок на ответ ставит сама POST-ручка, [контекстом](../glossary.md#g-context)
- [ ] Тесты: партия целиком через `httptest`, чужая cookie, чужой раунд, чужая комната

## Пять ручек

У заглушек общего состояния не было вовсе. Теперь оно нужно: реестр комнат `map[string]*Room`
из [m05-room-actor.md](m05-room-actor.md), интерфейс `store`, ключ подписи cookie, разметка
планшетов и канал `drain` из [m05-http-sse.md](m05-http-sse.md). Складывается это в структуру, у
которой ручки — методы; точный состав не зафиксирован. Пакетных переменных не заводим:
с ними тест не поднимет второй сервер рядом с первым.

**`POST /api/rooms`.** Сгенерировать код ([m05-session-room-codes.md](m05-session-room-codes.md)),
создать строку через `CreateRoom(code, boardID)`, поднять актора, ответить `{"code":"ABCD"}`.
Код занят — не 500, а повторить генерацию: у `store` на этот случай отдельная ошибка. Чем
выбирается планшет при создании, телом запроса или сервером, не решено.

**`POST /api/rooms/{code}/join`.** Ник приезжает телом, обратно уходит `Set-Cookie` с подписанным
`player_id` — механика в [m05-session-cookies.md](m05-session-cookies.md). Событие
`player_joined { player_id, name, slot }` пишет актор, ручка только просит. Пришла годная cookie —
это возвращение того же человека, а не второй игрок; иначе ломается «закрыл вкладку, открыл — та
же партия».

**`POST /api/rooms/{code}/moves`.** Главная ручка, разобрана ниже отдельно.

**`GET /api/rooms/{code}/stream`.** Поток сделан в [m05-http-sse.md](m05-http-sse.md), провод
к актору — в [m05-room-subscribers.md](m05-room-subscribers.md). Здесь остаётся то, что знает
только HTTP: **чей** это поток. [Проекция](../glossary.md#g-projection)
строится для конкретного игрока — в снапшоте есть поле `you`, — а `player_id` лежит в cookie.
Хвост для `Last-Event-ID` берётся уже из [лога](../glossary.md#g-log)
через `EventsSince`.

**`GET /api/boards/{id}`.** Отдать разметку планшета, неизвестный `id` — 404. Ни комнаты, ни
cookie тут нет. Отдельная ручка она потому, что разметка не ездит в снапшоте (договорённость
5 в [architecture.md](../architecture.md), раздел «Договорённости»): горы и руины за партию не
меняются, браузер забирает их один раз и держит фоном.

Какими статусами закрывать какие случаи, нигде не зафиксировано. Ошибка игрока и ошибка сервера —
разные статусы: «клетка занята», «нет такой комнаты», «негодная cookie» это 4xx, а не 500, иначе
журнал ошибок забьётся штатными ситуациями. Тело ошибки — тот же JSON, что и у остальных путей.

## Ход: что берём из тела, а что нет

Тело запроса:

```
POST /api/rooms/{code}/moves
{
  "round": 7,
  "target_board": "p1",
  "shape_id": "single",
  "rot": 0,
  "flip": false,
  "anchor": { "r": 4, "c": 7 },
  "terrain": "forest"
}
```

Поля `actor` здесь нет, хотя в ходе их два — `actor` и `target_board`. Это не пропуск: кто делает
ход, определяется подписанной cookie. Телу верить нельзя, `"actor": "p1"` напишет кто угодно и
будет ходить за него. `target_board` остаётся — он про то, на чьём поле рисуют, и разъедется
с `actor` на карте «Засада».

`round` — защита от дубликата: ход за уже закрытый раунд сервер молча выбрасывает. Бывает штатно:
игрок нажал дважды или браузер повторил запрос. Молча — без ошибки игроку: с его стороны ничего
плохого не случилось, а второй клетки на поле быть не должно.

Дальше ручка ничего не считает, а разговаривает с актором:

```go
func (h *Handler) postMove(w http.ResponseWriter, req *http.Request) {
    // ... разобрали JSON, нашли комнату ...

    reply := make(chan error, 1)
    room.inbox <- command{move: move, reply: reply}
    err := <-reply // ждём, пока горутина комнаты дойдёт до нас

    // ... отвечаем игроку ...
}
```

Нагружать успешный ответ телом не обязательно: снапшот всё равно приедет в поток, и для экрана
он [единственный источник истины](../glossary.md#g-truth).

## Грабли

Раздел «Грабли — здесь их больше всего» относится ко всему шагу 7 и почти весь разобран в
[m05-http-sse.md](m05-http-sse.md). Здесь — то, что стреляет при подключении настоящих ручек.

**Любой не-200 из ручки потока убивает клиента навсегда.** У заглушки промахнуться было негде, у
настоящей — сколько угодно: комната не нашлась, база не ответила, cookie не разобралась. Замерено
в Chrome: на 500, 404, 204 и даже на 200 с неправильным `Content-Type` `EventSource` вызывает
`onerror`, ставит `readyState === 2` и **больше не пробует никогда**. Отсюда порядок: все проверки
до первого байта ответа, а как только комната найдена — только 200 и `text/event-stream`. Всё,
что сломается дальше, уезжает сообщением `{"type":"error"}` внутрь потока, и поток закрывается.

**`reply` без [буфера](../glossary.md#g-chan-buffer) вешает комнату.**
Игрок закрыл вкладку, обработчик умер по отмене контекста, ответ никто не читает — и актор
навсегда виснет на записи в этот [канал](../glossary.md#g-channel). Виснет
не один запрос: актор один на комнату, значит встаёт вся партия, включая тех, у кого всё хорошо.
Поэтому `make(chan error, 1)` — положил и пошёл дальше. Одна цифра, и не написать её очень легко.

**Обёртка над [`ResponseWriter`](../glossary.md#g-responsewriter) без
`Unwrap()` ломает все потоки.** Вместе с ручками легко добавляется ещё одна
[middleware](../glossary.md#g-middleware) — «достать `player_id` из
cookie». Обычная обёртка, которая запоминает статус, —
`type rec struct { http.ResponseWriter; status int }` — и всё: `w.(http.Flusher)` через неё
возвращает `ok == false`, а `http.NewResponseController(w).Flush()` идёт по цепочке `Unwrap()`,
не находит её и возвращает `feature not supported`. У **каждой** обёртки должен быть
`func (w *rec) Unwrap() http.ResponseWriter`, и тест на поток гоняется через полную цепочку
middleware — голая ручка этого не поймает.

**Срок на ответ ставит ручка, а не сервер.** `WriteTimeout` не выставляем вовсе: замерено — 250 мс
при событиях раз в 400 мс, доехало одно из трёх, дальше `i/o timeout`. Отдельного
[таймаута](../glossary.md#g-timeout) на одну ручку в `net/http` нет, поле
лежит на `http.Server` и действует на все соединения сразу. Значит срок ставит сама POST-ручка —
контекстом с дедлайном. Не поставит никто — запрос, упершийся в базу, висит до ухода клиента.

**Контекст запроса нельзя тащить вглубь, до записи в базу.** Контексты запросов здесь отменяются
постоянно: закрыл вкладку, переподключился. Замерено: контекст, отменённый рядом с коммитом,
вернул ошибку — а строка **записалась**. Дальше `seq` в памяти и `seq` в базе расходятся навсегда,
каждая следующая запись натыкается на занятый номер. Лечится на стороне актора
([m05-store-events.md](m05-store-events.md)); ручке остаётся не тащить `req.Context()` дальше.

**Catch-all на `/` перехватывает опечатки в путях.** Шаблон `/` подходит к любому пути и любому
методу: вместо 405 на `DELETE /api/rooms` приходит 200 с `index.html`, а `res.json()` падает с
`Unexpected token '<'`. Проверка `strings.HasPrefix(r.URL.Path, "/api/")` написана ещё в
[m05-http-routing.md](m05-http-routing.md) — убедиться, что новые пути ей не перекрыты.

## Готово, когда

Сценарий — три терминала:

```sh
curl -X POST localhost:8080/api/rooms

# в отдельном терминале, оставить висеть
curl -N localhost:8080/api/rooms/ABCD/stream

# в третьем — отправить ход и посмотреть, как в потоке появился снапшот
curl -X POST localhost:8080/api/rooms/ABCD/moves -d '{...}'
```

- [ ] Первая команда возвращает код комнаты, и каждый раз новый
- [ ] `curl -i -c jar -X POST .../join -d '{"name":"Ваня"}'` — в ответе `Set-Cookie` с `HttpOnly`,
      `SameSite=Lax`, `Path=/`; с `-b jar` ход принимается, без cookie — нет, и это не 500
- [ ] В висящем `curl -N` после каждого хода появляется кадр с растущим
      [`id:`](../glossary.md#g-seq), а повтор того же хода нового кадра
      не даёт и ничего не ломает
- [ ] Двенадцать раундов подряд доводят партию до конца, в последнем снапшоте — счёт
- [ ] Убил сервер, поднял заново, подключился с той же cookie — партия та же
- [ ] Пока `curl -N` висит, `SIGTERM` останавливает сервер за доли секунды, а не за десять
- [ ] `go test ./internal/api/` — тест играет партию целиком через `httptest.NewServer`;
      `go test -race ./...` зелёный

Частные случаи удобно писать [таблицей](../glossary.md#g-table-test):
«запрос, cookie → ожидаемый статус». Строки на: чужая cookie, отсутствующая cookie, ход в закрытый
раунд, ход в несуществующую комнату, `GET /api/boards/nope`.
