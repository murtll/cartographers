## Зачем это

К этому моменту две половины лежат рядом и не соединены. Слева
[актор](../plans/20260728-cartographers-m05.md#g-actor) — одна
[горутина](../plans/20260728-cartographers-m05.md#g-goroutine), которая владеет состоянием
комнаты и умеет применить ход. Справа
[SSE](../plans/20260728-cartographers-m05.md#g-sse)-ручка — она умеет держать соединение
часами и слать в него кадры, но берёт их из временного канала-заглушки.

Эта задача — провод между ними. [Подписчик](../plans/20260728-cartographers-m05.md#g-subscriber)
это один открытый поток одного зрителя. Актор держит их список и после каждого изменения
рассылает всем свежий [снапшот](../plans/20260728-cartographers-m05.md#g-snapshot).

Без неё игра остаётся одиночной: ход применяется, в базу пишется, а на чужих экранах
ничего не происходит. И ещё: список подписчиков — вторая по популярности причина
[гонок](../plans/20260728-cartographers-m05.md#g-race) в таких серверах. Одна горутина
добавляет в срез нового зрителя, вторая в это время бежит по срезу и рассылает. Поэтому
список живёт внутри актора, и трогает его только он.

---

## Что делаем

- [ ] Поле `subscribers` в структуре комнаты, рядом с `state` и `seq`
- [ ] Подписка — сообщение в `inbox`, а не отдельный метод с
      [мьютексом](../plans/20260728-cartographers-m05.md#g-mutex)
- [ ] Отписка: подписчик ушёл — актор убирает его из списка
- [ ] Рассылка после каждого изменения состояния, каждому — своя
      [проекция](../plans/20260728-cartographers-m05.md#g-projection)
- [ ] Не влезло в [буфер](../plans/20260728-cartographers-m05.md#g-chan-buffer) — закрыть канал
      подписчика, соединение уронить
- [ ] Дедупликация по `seq` на стыке «подписался → доотправил пропущенное»
- [ ] Заменить временный источник кадров в SSE-ручке на настоящую подписку
- [ ] Тесты: два подписчика видят один и тот же ход; медленный подписчик отваливается, а
      комната живёт

## Подписка — это сообщение актору

Снаружи в поля комнаты никто не ходит. Значит и «добавь меня в список» — такое же
сообщение в `inbox`, как ход. Набросок структуры из плана:

```go
type Room struct {
    inbox chan command // единственная дверь внутрь

    // всё ниже трогает только run(). Снаружи к этим полям никто не ходит.
    state       game.State
    seq         int64
    subscribers []chan Snapshot
}
```

Что из этого следует для SSE-ручки: она вызывает что-то вроде `room.Subscribe(...)`,
получает обратно [канал](../plans/20260728-cartographers-m05.md#g-channel), из которого
читает в своём `select`, и на выходе — по `r.Context().Done()` или по `<-drain` — говорит
актору «меня больше нет». Внутри обе операции — просто ещё пара веток в `run()`.

Одна деталь ещё не зафиксирована. Проекция строится **для конкретного игрока**: в снапшоте
есть поле `you`, а порядок колоды не уезжает никому. Значит рядом с каналом надо помнить,
чей это поток. В плановом наброске `subscribers []chan Snapshot` такого поля нет — состав
структуры подписчика дорисовывается здесь, вместе с
[m05-room-projection.md](m05-room-projection.md).

Размер буфера у канала подписчика в плане тоже не выбран, и придумывать число тут нечего:
политика есть («рвём соединение, но не теряем событие»), а при какой глубине нормальный
клиент до разрыва никогда не доходит — до появления настоящих снапшотов не понять.

## Порядок пяти шагов

Обработка хода в акторе — это не одно действие:

```
1. проверить, что ход законный
2. записать событие в базу
3. обновить состояние в памяти
4. увеличить счётчик seq
5. разослать новый снапшот подписчикам
```

Рассылка — последняя, и это не вкусовщина. Поменяй местами 2 и 5 — игрок увидит свой ход,
запись не удастся, и после перезагрузки страницы ход исчезнет. Записали — случилось. Не
записали — игрок видит ошибку, а не призрак хода.

Рассылаем снапшот целиком, а не разницу. Партия это ~2 КБ, событий за игру ~35 — экономить
нечего, а кода вдвое меньше.

## Грабли

**Медленный подписчик: рвать соединение, а не выбрасывать событие.** Клиент может залипнуть:
ноутбук ушёл в сон, вкладка в фоне, канал забился. Актор в этот момент один на всю комнату,
и если он встанет на записи в забитый канал — встанет вся партия, включая тех, у кого всё
хорошо. Очевидная защита — неблокирующая отправка:

```go
select {
case ch <- ev:
default: // некому читать, пропускаем
}
```

Так делать нельзя. Если выброшенное событие окажется последним в раунде или финальным
подсчётом очков, следующего события не будет — и клиент останется в неправильном состоянии
молча и навсегда. [Heartbeat](../plans/20260728-cartographers-m05.md#g-heartbeat) при этом
продолжает ходить, TCP живое, `EventSource` ошибки не видит, не переподключается,
`Last-Event-ID` не шлёт — и весь механизм
[переигровки](../plans/20260728-cartographers-m05.md#g-replay) из
[лога](../plans/20260728-cartographers-m05.md#g-log), ради которого всё и строилось, ни разу
не срабатывает. Хуже обрыва: обрыв виден, а это нет.

Правильно наоборот: не влезло — **закрываем канал подписчика** и роняем его соединение.
Клиент переподключится и доберёт из лога. Рвать соединение безопасно, терять событие — нет.

Дальше по цепочке это выглядит так: SSE-ручка читает из канала через `v, ok := <-ch`,
видит `ok == false`, выходит из цикла и закрывает поток. Браузер сам создаёт соединение
заново и присылает `Last-Event-ID`. Всё, что для этого нужно, уже сделано в
[m05-http-sse.md](m05-http-sse.md).

**Порядок «подписаться → доотправить пропущенное».** Подписываться надо первым, иначе между
чтением лога и подпиской теряются события: пока ручка читает хвост из базы, кто-то ходит,
рассылка уходит в список, где этого подписчика ещё нет.

Но тогда оба потока идут одновременно и без дедупликации выдают события вперемешку —
замерено `[6 7 6 7]`. Клиент применит снапшот 6 последним и нарисует поле назад во времени.
Ошибка при этом не выглядит ошибкой: поток живой, кадры идут, просто на экране прошлое.

Лечится двумя строками: помнить максимальный уже отправленный
[`seq`](../plans/20260728-cartographers-m05.md#g-seq) и пропускать всё, что меньше или равно
ему. Дубликат безвреден, откат назад — нет.

**Тесты на таймеры — через `testing/synctest`.** Сюда заезжает тикер heartbeat и тикер
раунда, и без подмены времени тест начинает реально спать секундами. В Go 1.26
`testing/synctest` — стабильная часть
[стандартной библиотеки](../plans/20260728-cartographers-m05.md#g-stdlib), сделанная ровно
под нашу задачу: горутина-актор плюс таймер. Тридцать секунд игрового времени проходят за
ноль реального, и не надо тащить в боевой код
[интерфейс](../plans/20260728-cartographers-m05.md#g-interface) часов, чтобы подменить его
в тесте. Сам таймер раунда — соседняя задача, [m05-room-deadline.md](m05-room-deadline.md).

## Готово, когда

- [ ] Когда появятся ручки ([m05-http-api.md](m05-http-api.md)): два
      `curl -N localhost:8080/api/rooms/ABCD/stream` в двух терминалах — ход, отправленный
      третьим окном через `POST /api/rooms/ABCD/moves`, появляется в обоих потоках, и `id:`
      у кадра одинаковый
- [ ] Тест: подписчик, который не читает свой канал, получает **закрытый** канал, а не
      пропущенное событие. Второй подписчик в это время продолжает получать кадры
- [ ] Тест: комната после отвалившегося подписчика принимает ход и рассылает снапшот, то
      есть актор не встал
- [ ] Тест на дедупликацию: подписались, одновременно доотправили хвост из лога — в
      полученной последовательности `seq` строго возрастают, `[6 7 6 7]` не появляется
- [ ] Тест: подписчик отключился — его канал ушёл из `subscribers`. Сто подключений и сто
      отключений подряд не оставляют после себя ничего
- [ ] `go test -race ./internal/room/` зелёный. Гонки тут не «мы их избежали», а «неоткуда
      взять», и [детектор](../plans/20260728-cartographers-m05.md#g-race-detector) это должен
      подтверждать
- [ ] В SSE-ручке не осталось временного источника кадров из фазы 2

Тесты на рассылку удобно писать
[таблицей](../plans/20260728-cartographers-m05.md#g-table-test): «сколько подписчиков, кто из
них читает → какие `seq` каждый увидел».
