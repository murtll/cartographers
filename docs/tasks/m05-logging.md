# M0.5 · Конфиг и логи · Логи: формат, уровень, контекст

**Фаза 1.** Нужно сначала: ничего. Удобнее после [«Конфига из переменных окружения»](m05-config-env.md),
но можно и до — тогда две переменные читаются напрямую, а потом переедут в конфиг.
**Результат:** локально логи читаются глазами, в бою их разбирает машина, и понятно,
какой логгер брать в новом коде.

Пакет: `backend/cmd/server/` — плюс правило, которое действует на все остальные.

---

## Зачем это

Сейчас логгер создаётся так:

```go
log := slog.New(slog.NewTextHandler(os.Stdout, nil))
```

Здесь две проблемы, и обе тихие.

**Один формат на все среды.** Текстовый вывод удобно читать глазами и неудобно
разбирать машиной. В бою логи читает не человек: их грепают, фильтруют, скармливают
агрегатору. Разбирать `time=... level=INFO msg="board loaded" file=wildlands.json`
регулярками — занятие на любителя.

**`nil` вместо опций означает уровень Info.** То есть `log.Debug(...)` не печатает
**ничего**, вообще. Ловушка тут в том, что выглядит это как «код не выполняется»: ты
дописал отладочную строку, запустил, ничего не увидел и пошёл искать, почему не
вызывается функция. А она вызывается, просто уровень ниже порога.

---

## Что делаем

- [ ] `LOG_FORMAT` — `text` (по умолчанию) или `json`
- [ ] `LOG_LEVEL` — `debug` / `info` / `warn` / `error`, по умолчанию `info`
- [ ] Собрать логгер из этих двух и сразу позвать `slog.SetDefault`
- [ ] Записать правило «где дефолтный логгер, где свой с контекстом»
- [ ] Список того, что в логи не попадает никогда
- [ ] Проверить: `LOG_FORMAT=json` даёт то, что жуёт `jq`

Обёртка, которая пишет строку на каждый HTTP-запрос, — соседняя задача,
[m05-http-middleware.md](m05-http-middleware.md). Здесь решается, как эта строка
выглядит и что в неё можно класть.

## Два формата, потому что два читателя

Код один, отличается только хендлер:

```go
opts := &slog.HandlerOptions{Level: level}

var h slog.Handler
if format == "json" {
    h = slog.NewJSONHandler(os.Stdout, opts)
} else {
    h = slog.NewTextHandler(os.Stdout, opts)
}
log := slog.New(h)
```

Одно и то же событие в двух видах:

```
time=2026-08-03T15:05:53.074+03:00 level=DEBUG msg="board loaded" file=wildlands.json
{"time":"2026-08-03T15:05:53.074+03:00","level":"DEBUG","msg":"board loaded","file":"wildlands.json"}
```

Текст короче и читается без инструментов. JSON длиннее, зато `jq 'select(.level=="ERROR")'`
работает сразу, и поля не разъедутся, если в сообщение попадёт пробел или кавычка.

**Почему в `os.Stdout`, а не в файл.** Сервер живёт в контейнере, а контейнер отдаёт
наружу именно stdout — это то, что показывает `docker compose logs`. Файл внутри
контейнера прочитать некому, и он исчезнет вместе с контейнером.

## Уровень

`LOG_LEVEL` переменной, а не константой в коде, по одной причине: отлаживать приходится
и в бою тоже, а перезапуск с другой переменной дешевле пересборки образа.

Разбор строки в `slog.Level` — у него есть `UnmarshalText`, так что писать свой `switch`
не обязательно. Неизвестное значение должно быть ошибкой запуска, а не молчаливым
откатом на `info`: иначе опечатка `LOG_LEVEL=debgu` даст ровно ту же тишину, ради
избавления от которой всё и затевалось.

## Дефолтный логгер или свой с контекстом

Правило, по которому это решается, одно: **есть ли что прилепить через `With`.**

`With` создаёт логгер с намертво прилепленными полями:

```go
roomLog := log.With("room", code)
roomLog.Debug("round opened", "round", 7)   // room=ABCD round=7
roomLog.Debug("move submitted", "seq", 42)  // room=ABCD seq=42
```

Код комнаты попадает в каждую строку сам. Через пакетный `slog.Debug` то же самое
пришлось бы дописывать руками в каждый вызов — и однажды ты забудешь ровно в той строке,
которую потом будешь искать.

| место | какой логгер | почему |
|-------|--------------|--------|
| `boards.Load` | дефолтный, `slog.Debug(...)` | зовётся один раз на старте, прилепить нечего |
| миграции | дефолтный | то же самое: разовый прогон при запуске |
| `room.Room` | свой, полем: `log.With("room", code)` | все строки комнаты должны нести её код |
| `api.Handler` | свой, полем; обёртка добавляет метод и путь | у запроса есть свой контекст |
| `game`, разбор разметки | никакого | чистые функции, они возвращают ошибку, а не пишут в лог |

Логгер с контекстом держат **полем в структуре**, а не параметром функции:

```go
type Room struct {
    log *slog.Logger
    // ...
}

func NewRoom(code string, log *slog.Logger) *Room {
    return &Room{log: log.With("room", code)}
}
```

Тогда конструктор берёт его один раз, методы дёргают `r.log`, и сигнатуры не обрастают
параметром, который половина функций только передаёт дальше.

### Три оговорки про `SetDefault`

1. **Всё, что залогировано до вызова, уезжает мимо настроек.** Формат будет другой, и
   поток другой. Поэтому `SetDefault` — первым делом в `main`, до всего остального.
2. **Это глобальное состояние процесса.** Тест, который подменяет дефолтный логгер,
   нельзя гонять с [`t.Parallel()`](../glossary.md#g-tparallel) — он протечёт в соседние.
3. **Проверить тестом, чего в логах нет, с глобалкой неудобно.** Там, где такая проверка
   нужна, логгер должен передаваться — тогда в тест подсовывается буфер.

## Строка на каждый запрос к API

Что в ней должно быть: метод, путь, код ответа, длительность, размер ответа. Этого
хватает, чтобы ответить на «дошёл ли запрос, что ответили, сколько заняло» — то есть на
всё, что спрашивают первым делом.

Чего в ней быть не должно:

- **тела запроса** — в нём ход игрока, а на объёме это ещё и распухший лог;
- **query-строки целиком** — сегодня там пусто, завтра кто-нибудь передаст туда что-то
  чувствительное, и оно осядет в логах навсегда;
- **значения cookie** — это подписанная сессия, по логу её можно будет предъявить.

Код комнаты в отдельном поле класть можно и полезно: он не секрет, его игроки диктуют
друг другу голосом.

---

## Чего в логах не бывает никогда

Это не вкусовщина, а требования проекта:

- **`DATABASE_URL` целиком** — в нём пароль. Логировать можно хост и имя базы, но не
  строку подключения.
- **Ключ подписи cookie** — по нему подделывается любая сессия.
- **Payload события целиком.** В событии `game_started` лежит `deck_order` — порядок
  колоды, то есть ровно то, чего игрок знать не должен. В лог идут только `room_code`,
  `seq` и `type`.
- **Конфиг целиком** одной строкой — см. [m05-config-env.md](m05-config-env.md), там про
  это подробнее.

Логгер с прилепленным `room` тут помогает: когда контекст уже в логгере, в саму строку
не тянет положить «на всякий случай всё остальное».

---

## Готово, когда

- [ ] `go run ./cmd/server` без переменных — читаемый текст, уровень `info`
- [ ] `LOG_FORMAT=json go run ./cmd/server | jq .` — разбирается без ошибок
- [ ] `LOG_LEVEL=debug` показывает отладочные строки, без неё их нет
- [ ] `LOG_LEVEL=чтототакое` — сервер не стартует и говорит, что за значение не понял
- [ ] `slog.SetDefault` стоит первой строкой `main`, до загрузки разметки
- [ ] `grep -rn 'DATABASE_URL' backend/` — нигде не уходит в лог целиком
- [ ] В логах комнаты у каждой строки есть поле `room`
