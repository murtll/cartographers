# M0.5 · Комната · Актор: одна горутина на комнату

**Фаза 3.** Нужно сначала: [m05-game-loop.md](m05-game-loop.md),
[m05-store-events.md](m05-store-events.md).
**Результат:** состояние партии трогает ровно одна горутина, детектор гонок молчит.

Пакет: `backend/internal/room/`.

---

## Зачем это

`net/http` на каждый входящий запрос запускает отдельную
[горутину](../glossary.md#g-goroutine). Это не настройка, это как он
работает. Два игрока нажали на клетку в одну секунду — два запроса, две горутины и одно
состояние комнаты на двоих.

Обработка хода — не одно действие, а пять:

```
1. проверить, что ход законный
2. записать событие в базу
3. обновить состояние в памяти
4. увеличить счётчик seq
5. разослать новый снапшот подписчикам
```

Две горутины делают это вперемешку. Что ломается:

- **Счётчик [`seq`](../glossary.md#g-seq).** Обе прочитали 17, обе
  решили писать событие номер 18. Одна запишет, вторая получит ошибку от базы — спасибо
  составному первичному ключу. Но спас нас тут не код, а база; в памяти уже каша.
- **Список [подписчиков](../glossary.md#g-subscriber) SSE.** Одна
  горутина добавляет в срез нового зрителя, вторая в это время бежит по срезу и рассылает
  снапшот. Классика.
- **Любая мапа внутри состояния.** Одновременная запись в мапу в Go — это не «иногда
  неправильное значение», это `fatal error: concurrent map writes` и смерть всего
  процесса. Не паника, которую можно поймать через `recover`, а именно смерть: упавший
  сервер и все партии на нём разом.

## Что делаем

- [ ] Структура `Room`: `inbox`, состояние партии, `seq`, список подписчиков
- [ ] Тип `command`: что кладут в `inbox` и куда положить ответ
- [ ] `run(ctx)` — цикл `select`, единственное место, где живёт состояние
- [ ] `applyMove` — те самые пять шагов, вызывается только из `run`
- [ ] Заглушка `checkDeadline` по тикеру — сам дедлайн в [m05-room-deadline.md](m05-room-deadline.md)
- [ ] Реестр комнат: `map[string]*Room` под замком, старт и остановка горутины
- [ ] Тесты под `-race`: много горутин шлют ходы одновременно, состояние сходится

Свёртка, проекция и рассылка — отдельные задачи, они въезжают внутрь этого каркаса позже.

## Почему не мьютекс

Стандартный ответ на гонку — завести
[`sync.Mutex`](../glossary.md#g-mutex), брать его перед тем как
трогать состояние, отпускать через `defer`. Это работает, и большая часть кода в мире
написана именно так. Но:

- Замок надо не забыть **в каждом** месте, где трогают состояние. Забыл в одном — получил
  баг, который выстреливает раз в неделю под нагрузкой и не воспроизводится.
- Читая функцию, ты не видишь, взят замок или нет. Значит либо берёшь повторно (и
  получаешь [дедлок](../glossary.md#g-deadlock) — обычный
  `sync.Mutex` в Go не рекурсивный), либо не берёшь и надеешься.
- Все пять шагов должны быть одним неделимым куском, иначе смысла нет: замок всё равно
  держится через запись в базу. А таймер раунда трогает то же состояние из своей горутины
  — ещё одно место, где надо не забыть.

## Как устроен актор

Комнатой владеет одна горутина. Поля структуры трогает только она. Все остальные кладут
сообщение в канал и ждут ответа. Одно окно: очередь снаружи, внутри ровно один человек.

```go
type Room struct {
    inbox chan command // единственная дверь внутрь

    // всё ниже трогает только run(). Снаружи к этим полям никто не ходит.
    state       game.State
    seq         int64
    subscribers []chan Snapshot
}

type command struct {
    move  Move
    reply chan error // куда положить ответ; буфер 1, см. ниже
}

// run — единственное место, где живёт состояние комнаты.
func (r *Room) run(ctx context.Context) {
    tick := time.NewTicker(time.Second)
    defer tick.Stop()

    for {
        select {
        case cmd := <-r.inbox:
            cmd.reply <- r.applyMove(cmd.move)
        case <-tick.C:
            r.checkDeadline() // время раунда вышло — ставим клетку сами
        case <-ctx.Done():
            return // комната закрылась, горутина уходит
        }
    }
}
```

```go
// со стороны HTTP-обработчика:
reply := make(chan error, 1)
room.inbox <- command{move: move, reply: reply}
err := <-reply // ждём, пока горутина комнаты дойдёт до нас
```

Главное здесь: [`select`](../glossary.md#g-select) берёт **одну**
ветку за раз. Пока `applyMove` работает, остальные запросы просто лежат в канале. Значит
внутри `applyMove` ты один. Не «обычно один», а один по построению.
[Гонки](../glossary.md#g-race) не в том состоянии, что мы их
избежали — их физически неоткуда взять, потому что горутина одна. Замков в коде комнаты
нет вообще, и забыть их негде.

Состав `command` в [architecture.md](../architecture.md), «Актор: одна горутина на комнату»,
— эскиз: там только ход и ответ. Подписке на SSE тоже нужен путь
внутрь; поля в том же `command` или отдельные типы сообщений — не решено, решится в
[m05-room-subscribers.md](m05-room-subscribers.md). Решено другое: кроме `inbox`, пути внутрь нет.

## Почему здесь это дёшево

- Горутина стоит килобайты стека, не мегабайт как поток ОС: тысяча комнат — единицы мегабайт.
- Комнаты между собой ничем не связаны. Актор становится неудобным, когда акторам надо
  договариваться друг с другом; у нас этого нет совсем.
- Сообщений мало: одно на игрока раз в 10–30 секунд, очередь в `inbox` почти всегда пуста.
- Таймер раунда и подписка на SSE встают в тот же `select` — не нужна ни отдельная горутина
  под [тикер](../glossary.md#g-ticker), ни замок на подписчиков.

Один замок всё-таки будет: найти комнату по коду — это общая на весь сервер мапа
`map[string]*Room`. Она вне любого актора, к ней ходят все запросы. Вот её и закрываем
`sync.Mutex` (или берём `sync.Map` — что из двух, не решено), строк десять. Мьютекс на одну
мапу — нормально; неудобен он на состоянии, которое меняется пятью шагами и ещё по таймеру.

## Грабли

**Блокирующий вызов внутри цикла.** Запись в базу идёт внутри `applyMove`, и пока она идёт,
комната стоит: `select` уже выбрал ветку и до следующего сообщения не дойдёт. Для этой игры
нормально — ~35 записей за партию, каждая пара миллисекунд. Но если в актор когда-нибудь
заедет что-то на секунды, это заметят все в комнате. Лечится выносом наружу, а не «ещё одной
горутиной»: вторая горутина внутри комнаты — ровно тот общий доступ к состоянию, ради отсутствия
которого всё затевалось.

**Актор пишет сам себе.** Если внутри `applyMove` положить сообщение в свой же `inbox` и ждать
ответа — комната висит навсегда. Ответ в этот канал кладёт только `run`, а `run` в этот момент
стоит внутри `applyMove` и до следующего витка `select` не дойдёт. Отвечать некому. Правило:
актор в свой канал не пишет.

**`reply` без [буфера](../glossary.md#g-chan-buffer).** Игрок закрыл
вкладку, обработчик умер по отмене [контекста](../glossary.md#g-context),
никто не читает ответ — и актор навсегда виснет на записи в этот канал. Виснет не запрос, а вся комната:
горутина-то одна. Поэтому `make(chan error, 1)`: положил и пошёл дальше, даже если ответ
уже никому не нужен.

**Горутина не умирает.** Комната, в которую час никто не заходил, должна закрыться. Отсюда
`ctx.Done()` в `select` — **и** что-то, что этот контекст отменяет. Одной ветки мало: если
контекст никто не отменяет, горутина тикает вечно, и за неделю аптайма набирается мусор.
Через сколько именно закрывать — не решено.

**Безразмерный `inbox`.** Небольшой буфер нужен, чтобы отправитель не ждал. Но большой
буфер просто прячет затык: очередь растёт, игроки ждут ответа секундами, а по метрикам всё
хорошо — сервер же принимает запросы. Конкретный размер буфера не зафиксирован.

**Контекст запроса не должен доезжать до базы.** Это грабли
[m05-store-events.md](m05-store-events.md), но выстреливают они
здесь. Под SSE контексты запросов отменяются постоянно. Замерено: контекст, отменённый
рядом с коммитом, вернул ошибку — а строка **записалась**. `seq` нумеруется в памяти,
значит после «ошибки» актор оставит у себя старый номер, в базе он уже занят, и
расхождение навсегда. Актор пишет в базу под своим временем жизни (`context.WithoutCancel`
от базового контекста сервера), а на **любую** ошибку `Append` не гадает, а перечитывает
лог через `EventsSince`: источник истины — база, не память.

## Готово, когда

- [ ] `go test -race ./internal/room/` зелёный. И `go test -race ./...` тоже
- [ ] Тест: 50 горутин одновременно шлют ход в одну комнату.
      [Детектор гонок](../glossary.md#g-race-detector) молчит,
      `seq` в конце равен числу принятых ходов, а не «примерно столько»
- [ ] Тест: отменили контекст комнаты — `run` вышел. Проверять закрытием канала в конце
      `run`, а не `sleep`
- [ ] Тест: ответа из `reply` никто не читает — комната принимает следующую команду.
      С таймаутом, чтобы висящая комната падала, а не висела вместе с тестом
- [ ] Тест: параллельные обращения к реестру по одному коду дают **один и тот же**
      `*Room`, а не два актора на одну партию
- [ ] `grep -rn 'sync\.' backend/internal/room/ --exclude='*_test.go'` показывает только реестр

Пока свёртки нет, `applyMove` в тестах — заглушка, которая увеличивает `seq`.
