## Зачем это

Партия хранится не как текущее состояние, а как список того, что случилось, по порядку —
[лог событий](../plans/20260728-cartographers-m05.md#g-log). Подход целиком называется
[event sourcing](../plans/20260728-cartographers-m05.md#g-event-sourcing), лог в базе —
[источник истины](../plans/20260728-cartographers-m05.md#g-truth).
[**Свёртка**](../plans/20260728-cartographers-m05.md#g-fold) — дорога обратно: взять
пустую партию и применить события одно за другим, пока не получится то, что сейчас.

Состояния партии в базе нет вообще. В `rooms` четыре колонки — `id`, `code`, `board_id`,
`created_at`. Ни фазы, ни раунда, ни нарисованного. Всё это существует только как
результат свёртки.

Что не работает, пока этой задачи нет:

1. **Перезапуск бэкенда убивает партию.** [Актор](../plans/20260728-cartographers-m05.md#g-actor)
   держит состояние в полях структуры, то есть в памяти процесса. Процесс кончился — партия
   кончилась. В чек-листе шага 10 это отдельный пункт: «Перезапустить контейнер бэкенда →
   партия жива».
2. **Комнату неоткуда взять при втором обращении.** [Горутина](../plans/20260728-cartographers-m05.md#g-goroutine)
   комнаты, в которую час никто не заходил, должна закрыться, иначе за неделю аптайма
   набирается мусор. Игрок вернулся, лог в базе полный — а собрать из него комнату нечем.
3. **Некому решать, кто этот игрок.** Членство в комнате и место игрока восстанавливаются
   свёрткой событий `player_joined`, и это единственный источник истины. Cookie
   подтверждает только «это тот же человек, что и раньше».
4. **Ошибку записи нечем лечить.** Правило из шага 5: на любую ошибку `Append` не гадать,
   а перечитать лог через `EventsSince`. Перечитать — значит свернуть.

## Что делаем

- [ ] Описать семь типов событий структурами Go, по одной на тип
- [ ] Реестр `строка → структура Go`: неизвестный тип при чтении — ошибка, а не пропуск
- [ ] Написать применение одного события к состоянию — по случаю на каждый тип
- [ ] Восстановление: при первом обращении прочитать лог из базы и свернуть с нуля
- [ ] После восстановления взять [`seq`](../plans/20260728-cartographers-m05.md#g-seq) из
      последнего события лога, а не начинать с нуля
- [ ] На любую ошибку `Append` — выбросить состояние из памяти и свернуть заново
- [ ] Тесты: [JSON](../plans/20260728-cartographers-m05.md#g-json) туда-обратно на каждый
      тип, «пережили перезапуск», неизвестный тип события

## Семь событий

```
room_created    { board_id }
player_joined   { player_id, name, slot }
game_started    { seed, deck_order }   ← в проекцию не попадает
round_opened    { round, options, constraint }
move_submitted  { actor, target_board, shape_id, rot, flip, anchor, terrain }
round_closed    { round }
game_ended      { scores }
```

Список закрыт не только в Go: в схеме на нём стоит
[`CHECK`](../plans/20260728-cartographers-m05.md#g-check) `events_type_valid`, и база не
примет восьмой тип. Добавить событие — это миграция, а не строчка в коде. Поля события
лежат в [`jsonb`](../plans/20260728-cartographers-m05.md#g-jsonb): у разных типов они
разные. Внутрь payload запросами не лазим — читаем лог комнаты целиком и разбираем в Go.

Пометка «в проекцию не попадает» у `game_started` — не про свёртку: `deck_order` она
применяет обязательно, иначе неоткуда взять колоду. Прячет его
[проекция](../plans/20260728-cartographers-m05.md#g-projection),
[m05-room-projection.md](m05-room-projection.md).

## Как выглядит свёртка

```go
var state game.State          // пустая партия
for _, ev := range events {
    state = apply(state, ev)  // одно событие — один шаг
}
```

Имена и сигнатуры план не фиксирует. Известно только, что в структуре комнаты есть поля
`state game.State`, `seq int64` и `subscribers []chan Snapshot` и трогает их одна горутина.

Три свойства, за которые надо держаться:

**Свёртка ничего не делает наружу.** Не пишет в базу, не рассылает
[снапшоты](../plans/20260728-cartographers-m05.md#g-snapshot), не заводит таймер. Иначе
подъём комнаты после перезапуска запишет весь лог в базу второй раз и вывалит подписчикам
пять старых снапшотов подряд — партия на глазах у игрока переиграется с начала.

**Свёртка детерминирована.** Одинаковый лог — одинаковое состояние, всегда. Никакого
`time.Now()`, никакого `rand` внутри. Ровно поэтому в `game_started` лежит готовый
`deck_order`, а не один только `seed`: колоду свёртка читает из лога, а не тасует заново.
Если тасовать её при подъёме комнаты, после перезапуска партия продолжится другой
колодой, а лог будет выглядеть невинно.

**Состояние в памяти — это кеш.** Производное, выбрасывается в любой момент. Если память и
лог разошлись, прав лог, и память надо не подправить руками, а собрать заново.

### Порядок в живой партии

```
проверить → записать в базу → обновить состояние → разослать снапшот
```

Порядок «сначала в базу, потом рассылка» важен: наоборот игрок увидит свой ход, а запись
не удастся, и после перезагрузки ход исчезнет. Записали — случилось. Не записали — игрок
видит ошибку.

Шаг «обновить состояние» — та же функция применения события, что и в свёртке, а не вторая
её копия. Копии однажды разъедутся на одном случае, и симптом будет такой: пока сервер
жив, всё правильно, после перезапуска счёт другой.

## Что уже решено

**Промежуточных снапшотов в базе нет.** За партию ~35 событий, состояние ~2 КБ, свёртка с
нуля делается раз на подъём комнаты. Кеш состояния был бы вторым местом, которое может
разойтись с логом.

**`seq` нумерует актор в памяти.** База только страхует: `PRIMARY KEY (room_id, seq)` не
даст двум процессам записать событие с одинаковым номером. Отсюда пункт «взять `seq` из
последнего события»: оставил счётчик нулевым — первый же ход упрётся в занятый номер.

**Раунд — отдельное событие, а не «карта = ход»** (договорённость 4). Значит в свёртке есть
и `round_opened`, и `round_closed`, а поле `constraint` пока всегда пустое.

**Ход применяется к полю `target_board`, а не `actor`** (договорённость 2). Сейчас они
всегда равны, но смотреть надо в `target_board` уже сегодня — иначе на карте «Засада»
монстры нарисуются не туда.

**Разметку планшета в лог не пишем.** За партию она не меняется и не едет даже в снапшот
(договорённость 5). В логе есть `board_id` из `room_created`, разметка берётся по нему из
`boards`. Без неё не работает проверка хода: клетка свободна, только если там нет
нарисованного **и** нет горы или ущелья.

Состав `game.State` план не описывает. Из шага 4 известно только: поле игрока —
`[11][11]Terrain` плюс ссылка на разметку, счёт пока — число закрашенных клеток.

## Грабли

**Ошибка `Append` не значит «не записалось».** Под [SSE](../plans/20260728-cartographers-m05.md#g-sse)
[контексты](../plans/20260728-cartographers-m05.md#g-context) запросов отменяются
постоянно: закрыл вкладку, переподключился. Замерено: контекст, отменённый рядом с
коммитом, вернул ошибку — а строка **записалась**. Дальше самое неприятное: `seq` у нас
нумеруется в памяти, значит после «ошибки» актор оставит у себя старый номер, а в базе он
уже занят, и расхождение навсегда. Отсюда два правила. Актор пишет в базу под своим
временем жизни — `context.WithoutCancel` от базового контекста сервера, а не `r.Context()`.
И на **любую** ошибку `Append` не гадать, а перечитать лог через `EventsSince`. Это и есть
причина, по которой свёртка — отдельная функция, а не код внутри старта комнаты: её зовут
не только при подъёме, но и в обработке ошибок.

**Молчаливый пропуск при чтении лога.** `RowToStructByNameLax` забивает нулями: забыл
колонку `payload` в `SELECT` — получил событие с пустым payload и `err == nil`. Свёртка
такое событие применит, состояние молча разойдётся с логом, и искать будет негде. Только
строгий `RowToStructByName`, и колонки перечислять руками, без `SELECT *`. То же и с
реестром типов: неизвестный тип — ошибка, а не пропуск. Лучше комната, которая не
поднялась с внятной ошибкой, чем комната с дыркой в истории.

**Выброшенное событие ломает всю переигровку.** Грабля разбирается в
[m05-room-subscribers.md](m05-room-subscribers.md), но упирается сюда. Очевидная защита от
залипшего клиента — неблокирующая отправка:

```go
select {
case ch <- ev:
default: // некому читать, пропускаем
}
```

Так делать нельзя. Если выброшенное событие окажется последним в раунде или финальным
подсчётом очков, следующего не будет — и клиент останется в неправильном состоянии молча и
навсегда. [Heartbeat](../plans/20260728-cartographers-m05.md#g-heartbeat) при этом
продолжает ходить, TCP живое, `EventSource` ошибки не видит, не переподключается,
`Last-Event-ID` не шлёт — и весь механизм
[переигровки](../plans/20260728-cartographers-m05.md#g-replay) из лога, ради которого всё и
строилось, ни разу не срабатывает. Правильно наоборот: не влезло — закрываем канал
подписчика и роняем соединение, клиент переподключится и доберёт из лога. Там же вторая
половина: подписываться надо **до** дочитывания лога, иначе события между чтением и
подпиской теряются, — а чтобы два потока не выдали вперемешку замеренное `[6 7 6 7]`,
помнить максимальный уже отправленный `seq` и пропускать всё, что меньше или равно.

## Готово, когда

- [ ] `go test ./internal/room/` зелёный, `go test -race ./internal/room/` тоже:
      [детектор гонок](../plans/20260728-cartographers-m05.md#g-race-detector) молчит
- [ ] Тест «пережили перезапуск»: пять ходов, выбросить объект комнаты, поднять из базы,
      состояние то же. Сравнивать состояние целиком, а не «раунд совпал»
- [ ] Тест: после подъёма `seq` равен номеру последнего события лога. Иначе первый же ход
      упрётся в `PRIMARY KEY (room_id, seq)`
- [ ] Тест «структуру в JSON и обратно — то же самое», по одному на каждый из семи типов.
      Двадцать строк, ловят опечатку сразу, а не через месяц
- [ ] Тест: в логе событие с типом, которого нет в реестре → подъём комнаты возвращает
      ошибку, а не комнату с дыркой
- [ ] Тест: после подъёма колода взята из `deck_order`, а не перетасована заново
- [ ] Руками: `docker compose up -d`, сыграть пару ходов, `docker compose restart backend`,
      обновить вкладку — поле то же
- [ ] `docker compose exec db psql -U cartographers -d cartographers -c 'select seq, type from events order by seq'`
      — события идут подряд, без дырок в нумерации

Применение события к состоянию удобно проверять
[таблицей](../plans/20260728-cartographers-m05.md#g-table-test): «лог → каким должно стать
состояние». Тесты на дедлайн раунда сюда не лезут — они через `testing/synctest` и живут в
[m05-room-deadline.md](m05-room-deadline.md).
